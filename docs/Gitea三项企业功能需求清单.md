# Gitea 三项企业功能需求清单

## 1. 文档目的

本文将《Gitea 三项企业功能：详细需求与开发计划》拆分为可追踪、可判定、可直接映射测试用例的原子需求清单，覆盖审批规则、多层级组织与权限继承、详细操作审计，以及共同基础、升级迁移、性能可靠性和交付要求。

本文是测试设计输入，不代表功能已经实现或通过验收。每条测试用例应至少关联一个需求编号；每个需求编号应至少有一个正向、反向或边界测试覆盖。涉及并发、故障恢复、安全边界的需求不得只用界面模拟或接口返回值判定，应核对数据库、Git 引用、真实 HTTP/SSH 访问或外送接收结果。

## 2. 状态和优先级约定

| 标记 | 含义 |
|---|---|
| `[ ]` | 尚未提供验收证据 |
| `[x]` | 已有可复核证据证明通过 |
| `必须` | 不满足则不能进入正式发布 |
| `应当` | 重要需求；若暂缓，必须记录差异、影响和批准人 |
| `排除` | 本期明确不实现，但需验证没有被误宣称支持 |

测试结果建议使用：`通过`、`失败`、`阻塞`、`未执行`、`不适用`。`阻塞`和`不适用`必须写明依据，不能用来隐藏未覆盖需求。

### 2.1 冻结基线值

| 项目 | 固定值 |
|---|---|
| Gitea 版本 | `1.27.3` 正式版 |
| 基础镜像 | `docker.io/gitea/gitea:1.27.3@sha256:d584940b7143982682ac4541509dd628506c2b568221e6af41e5a2ead1de4fe7` |
| 语义对照版本 | GitLab Self-Managed Ultimate `19.3.2` |
| 部署平台 | Linux amd64、Docker Compose、PostgreSQL |
| 容量目标 | 1,000 名研发、500 人峰值活跃、1,000 人活跃压力测试 |

固定治理接口族：

- `/api/v1/governance/capabilities`
- `/api/v1/governance/groups`
- `/api/v1/governance/repositories/{id}/approval-rules`
- `/api/v1/governance/pulls/{id}/approval-state`
- `/api/v1/governance/audit-events`
- `/api/v1/governance/audit-streams`
- `/api/v1/governance/audit-exports`

原始需求所依据的上游版本入口：[Gitea 1.27.3](https://github.com/go-gitea/gitea/releases/tag/v1.27.3)、[GitLab 19.3.2](https://docs.gitlab.com/releases/patches/patch-release-gitlab-19-3-2-released/)。后续测试设计应使用冻结的语义对照矩阵，不应在没有变更评审的情况下随上游在线文档漂移。

## 4. 审批规则需求清单

### 4.1 规则定义与适用范围

| 状态 | 编号 | 优先级 | 原子需求 | 主要验收点 |
|---|---|---|---|---|
| [ ] | APR-001 | 必须 | 每个项目支持创建、查看、修改、启停和删除多条审批规则。 | 多规则并存时 CRUD 互不覆盖，历史 PR 行为符合版本语义。 |
| [ ] | APR-002 | 必须 | 每条规则包含名称、审批人、审批组、所需人数、目标分支范围和启用状态。 | 保存后回读字段完整且判定使用同一数据。 |
| [ ] | APR-003 | 必须 | 审批人和审批组使用稳定 ID 关联，不以可变名称作为身份键。 | 人员/群组改名后规则仍指向原对象。 |
| [ ] | APR-004 | 必须 | 规则支持全部分支。 | 对任意目标分支的 PR 均适用。 |
| [ ] | APR-005 | 必须 | 规则支持全部保护分支。 | 新增保护分支后无需改规则即可适用。 |
| [ ] | APR-006 | 必须 | 规则支持指定保护分支。 | 仅命中的指定分支适用。 |
| [ ] | APR-007 | 必须 | 规则支持保护分支规则匹配。 | 通配或规则变更后的适用范围确定且可解释。 |
| [ ] | APR-008 | 必须 | 来自 Fork 的 PR 使用目标项目的规则、设置和策略。 | Fork 来源不能降低目标项目要求。 |
| [ ] | APR-009 | 必须 | 支持项目默认规则和单个 PR 规则。 | 新 PR 初始规则及 PR 自身规则来源可区分。 |
| [ ] | APR-010 | 必须 | 允许覆盖时，PR 保存自身规则版本。 | 项目默认规则变化后的既有 PR 行为符合冻结语义。 |
| [ ] | APR-011 | 必须 | 禁止覆盖时，既有 PR 按冻结的 GitLab 更新语义同步规则。 | 项目规则修改后 PR 状态重新计算且来源明确。 |
| [ ] | APR-012 | 必须 | 实例级和顶级群组可以下发并锁定审批设置。 | 后代项目可见来源，不能越权修改锁定项。 |
| [ ] | APR-013 | 必须 | 群组强制审批策略覆盖所有后代项目。 | 新建、移动进入或深层后代项目均受约束。 |
| [ ] | APR-014 | 必须 | 子项目和 PR 作者不能降低上级强制审批要求。 | UI、API 和直接请求均拒绝降级。 |
| [ ] | APR-015 | 必须 | 审批设置继承与审批规则实体分别建模和展示。 | 来源、覆盖、锁定和计票信息不混淆。 |

### 4.2 计票与不可满足规则

| 状态 | 编号 | 优先级 | 原子需求 | 主要验收点 |
|---|---|---|---|---|
| [ ] | APR-016 | 必须 | 支持指定人员逐个必批。 | 每位指定人员分别形成不可替代的必批要求。 |
| [ ] | APR-017 | 必须 | 支持每个审批组独立设置所需人数。 | 多组要求分别计票，全部满足才通过。 |
| [ ] | APR-018 | 必须 | 所有适用的必需规则必须同时满足。 | 满足部分规则时仍阻止合并并显示缺项。 |
| [ ] | APR-019 | 必须 | 同一用户在同一规则内最多计一票。 | 重复批准或多身份映射不能增加票数。 |
| [ ] | APR-020 | 必须 | 同一合格用户可以同时满足多条不同规则。 | 重叠组与指定人场景按规则分别达标。 |
| [ ] | APR-021 | 必须 | 若配置总人数要求，总人数按不同用户去重。 | 一人满足多规则时总人数仍只增加一。 |
| [ ] | APR-022 | 必须 | 所需人数合法范围为 0 至 100。 | 边界值可保存，范围外及非整数输入被拒绝。 |
| [ ] | APR-023 | 必须 | 所需人数为 0 时表示可选审批，不阻止合并。 | 无批准仍可通过此规则，且不影响其他门禁。 |
| [ ] | APR-024 | 必须 | 页面明确区分可选规则和必需规则。 | 状态、文案和缺项展示无歧义。 |
| [ ] | APR-025 | 必须 | 指定必批人员离职、停用或失去资格时规则进入“需要处理”并阻断合并。 | 不自动视为满足或静默删除要求。 |
| [ ] | APR-026 | 必须 | 审批组为空或合格人数少于要求时进入“需要处理”并阻断合并。 | 页面给出不可满足原因及可修复入口。 |
| [ ] | APR-027 | 必须 | 只有具备规则管理权限的用户可以修复不可满足规则。 | 普通成员不能通过修改规则解除阻断。 |

### 4.3 审批资格与身份生命周期

| 状态 | 编号 | 优先级 | 原子需求 | 主要验收点 |
|---|---|---|---|---|
| [ ] | APR-028 | 必须 | 审批组只按该组直接成员构成审批池。 | 继承成员不自动进入审批池。 |
| [ ] | APR-029 | 必须 | 审批组不自动包含其所有子组成员。 | 子组成员无直接成员资格时不得计票。 |
| [ ] | APR-030 | 必须 | 单独指定用户计票前必须验证其真实项目访问资格。 | 仅出现在候选列表但无有效访问权时不得计票。 |
| [ ] | APR-031 | 必须 | 支持满足访问条件的 Reporter 审批。 | Reporter 的批准资格与推送/合并权限独立。 |
| [ ] | APR-032 | 必须 | 支持满足访问条件的 Planner 审批。 | Planner 按能力判定，不能按角色数字粗略比较。 |
| [ ] | APR-033 | 必须 | 用户停用后立即重新计算其已有批准有效性。 | 新请求不得继续使用旧有效缓存。 |
| [ ] | APR-034 | 必须 | 成员资格到期后立即重新计算其已有批准有效性。 | 到期边界前后结果与时间一致。 |
| [ ] | APR-035 | 必须 | 用户移出审批组后立即重新计算其已有批准有效性。 | 票数、缺项和合并状态同步变化。 |
| [ ] | APR-036 | 必须 | 用户项目访问被撤销后立即重新计算其已有批准有效性。 | 页面/API/最终授权结果一致。 |
| [ ] | APR-037 | 必须 | PR 作者默认不能批准自己的 PR。 | 页面和接口均拒绝或不计票。 |
| [ ] | APR-038 | 必须 | 提交者能否批准由独立设置控制。 | 开关两种状态及与作者重叠场景均正确。 |
| [ ] | APR-039 | 必须 | 批准、撤回、请求修改和评审历史复用 Gitea 原生能力。 | 不出现第二套互不一致的按钮、记录或状态。 |
| [ ] | APR-040 | 必须 | 支持配置“再次认证后批准”。 | 未完成再认证的批准请求被拒绝。 |
| [ ] | APR-041 | 必须 | 再次认证复用当前实例实际可用的认证方式。 | 不引入本期排除的身份系统依赖。 |
| [ ] | APR-042 | 必须 | 实例没有可用再认证方式时拒绝启用该设置。 | 返回明确错误且不保存半生效配置。 |

### 4.4 新代码、差异版本和规则变化

| 状态 | 编号 | 优先级 | 原子需求 | 主要验收点 |
|---|---|---|---|---|
| [ ] | APR-043 | 必须 | 默认在 PR 代码差异发生变化后取消已有批准。 | 新提交改变差异后批准失效并记录原因。 |
| [ ] | APR-044 | 必须 | 仅改变提交历史但差异不变的 rebase 按差异识别结果决定是否保留批准。 | 使用真实 diff 验证，不只比较提交 SHA。 |
| [ ] | APR-045 | 必须 | 每次批准保存对应提交、差异版本和规则依据。 | 可追溯当时批准覆盖的代码及要求。 |
| [ ] | APR-046 | 必须 | 差异发生 `A → B → A` 时，已失效批准不能自动复活。 | 回到旧差异仍需重新批准。 |
| [ ] | APR-047 | 必须 | 修改 PR 目标分支后立即重新计算审批状态。 | 新目标规则和保护条件生效。 |
| [ ] | APR-048 | 必须 | 修改审批人或审批组后立即重新计算审批状态。 | 被移除来源的批准不再错误满足。 |
| [ ] | APR-049 | 必须 | 修改所需人数后立即重新计算审批状态。 | 增减人数均实时反映。 |
| [ ] | APR-050 | 必须 | 影响审批资格的权限变化后立即重新计算。 | 权限修订号变化后旧缓存无效。 |
| [ ] | APR-051 | 必须 | 规则来源或上级策略变化后立即重新计算。 | 新增、移除、锁定变化都有明确结果。 |

| 状态 | 编号 | 优先级 | 原子需求 | 主要验收点 |
|---|---|---|---|---|
| [ ] | APR-052 | 必须 | 网页合并入口执行统一审批检查。 | 未满足时不能更新目标引用。 |

| [ ] | APR-056 | 必须 | 审批达标后仍须满足 CI 条件。 | 审批不能覆盖失败或未完成 CI。 |
| [ ] | APR-057 | 必须 | 审批达标后仍须满足无冲突条件。 | 冲突 PR 不能合并。 |
| [ ] | APR-058 | 必须 | 审批达标后仍须满足“请求修改”状态约束。 | 未解除的请求修改继续阻断。 |
| [ ] | APR-059 | 必须 | 审批达标后仍须满足原生分支保护及其他既有门禁。 | 新功能不能弱化原生保护。 |
| [ ] | APR-060 | 必须 | 启用“必须审批后进入目标分支”时检查直接推送。 | 未授权提交不能通过 HTTP/SSH push 进入分支。 |
| [ ] | APR-061 | 必须 | 启用该配置时检查强制推送。 | `--force`、删除/重建引用不能绕过。 |

| [ ] | APR-063 | 必须 | 其他原生绕过名单不能绕过强制审批，除非需求明确允许并审计。 | 逐类验证实际配置项。 |
| [ ] | APR-064 | 必须 | 撤回先提交完成时，后续最终合并授权必须拒绝。 | 并发顺序和结果可由持久记录证明。 |
| [ ] | APR-065 | 必须 | 成员撤权先提交完成时，后续最终合并授权必须拒绝。 | 不使用旧权限缓存放行。 |
| [ ] | APR-066 | 必须 | 规则修改先提交完成时，后续最终合并授权必须按新规则判定。 | 合并不能跨越新修订号。 |

| [ ] | APR-070 | 必须 | 最终合并授权使用数据库锁和持久化授权记录确定操作顺序。 | 多进程/多请求下不依赖单进程内存锁。 |

| [ ] | APR-072 | 必须 | 授权记录在 Git 操作完成并核对前持续存在。 | 超时不会过早释放授权导致相反操作穿越。 |
| [ ] | APR-073 | 必须 | 网络超时、进程退出或结果不明时先核对实际 Git 引用。 | 恢复结论与真实目标引用一致。 |
| [ ] | APR-074 | 必须 | 结果不明时不得自动重复执行合并。 | 不产生重复副作用或错误审计。 |

## 12. 测试用例映射要求

### 12.1 用例最小字段

后续测试用例至少包含以下字段：

| 字段 | 要求 |
|---|---|
| 用例编号 | 唯一且稳定，例如 `TC-APR-001-POS-01` |
| 需求编号 | 引用本文一个或多个编号，不允许为空 |
| 测试级别 | 单元、组件、接口、端到端、迁移、性能、持续运行、安全或故障注入 |
| 前置条件 | 版本、拓扑、角色、路径、规则、数据规模和功能开关 |
| 测试数据 | 使用稳定 ID，并写明成员关系、权限来源和差异版本 |
| 操作步骤 | 包含真实入口；并发用例写清先后控制点 |
| 预期结果 | 可观察且可判定，避免“正常”“正确”等模糊表述 |
| 后置核对 | 数据库、Git 引用、页面、API、HTTP/SSH Git、审计或外送结果 |
| 证据 | 请求/响应、日志、查询结果、截图、引用值、事件 ID 和时间线 |
| 清理与恢复 | 不破坏首次失败证据；说明是否可重复执行 |
| 执行环境 | 源码、候选镜像、最终镜像、隔离现场或生产现场 |
| 状态与缺陷 | 通过、失败、阻塞、未执行、不适用及关联缺陷编号 |

### 12.2 测试组合规则

- 每条功能需求至少有一个正向用例；包含“拒绝、不得、不能、阻止”的需求至少有一个反向用例。
- 数值范围必须覆盖最小值、最大值、刚好越界和非法类型。
- 权限测试至少覆盖匿名用户、无权用户、直接成员、继承成员、共享成员、继承共享成员、资源管理员和实例管理员中的适用角色。
- 路径测试至少覆盖 1 层、5 层、20 层、重名短路径、改名别名、移动和转移。
- 审批测试至少覆盖指定人、单组、多组、重叠成员、总人数去重、空组、人数不足、成员到期、撤权和 `A → B → A`。
- 写入与并发测试必须覆盖请求前、最终检查前、取得授权后、Git 更新后但回执前、审计提交前后等关键故障点。
- 审计测试同时验证“业务事实存在时有事件”和“业务事实不存在时不虚构成功事件”。
- 迁移测试必须保存升级前快照、升级差异、升级后事实和回退/恢复结果。
- 性能结果必须报告总请求数、完成数、失败数、活跃独立身份、分位延迟、资源限制和测试持续时间。
- 模拟测试、源码检查、接口成功、候选镜像运行和真实目标环境验收分别标记，不能互相替代。

## 13. 需求变更规则

- 新增需求必须分配新编号；已经用于测试或缺陷追踪的编号不得复用。
- 修改需求语义时记录变更日期、原因、影响用例和重新验收范围。
- 删除或延期需求时保留原条目，标记状态和批准依据，不直接从清单移除。
- GitLab 对照语义、Gitea 上游行为或支持范围变化时，先更新冻结对照矩阵，再调整实现和测试。
- 任何尚无真实证据的条目保持 `[ ]`，不得因另一个版本、模拟环境或相邻功能通过而标记完成。
