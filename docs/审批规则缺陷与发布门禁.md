# 审批规则缺陷与发布门禁

## APR-RACE-001：最终检查后撤回审批或失去组资格，在途合并仍完成

- 当前级别：P2（2026-09-13 复评）。
- 状态：已复现、暂缓修复、后续必修；未关闭。
- 决策：用户允许继续外接功能开发和隔离测试，继续复用原生审批；没有接受带此缺陷正式启用生产强制审批。
- 首次评估：第一阶段按“直到引用写入前撤回都阻断”的严格条件评为 P1。原报告和首次证据保留，不回写历史结果。本次针对已获批代码的有限在途窗口复评为 P2，实际触发频率尚未测量。
- 触发：原生要求三票；四名批准者满足两个必需组；Hook 最后检查通过后，指定组唯一批准被撤回或该批准者移出组；原生票数仍满足，但指定组缺票，实际目标引用仍更新。
- 影响：撤回或移组已成功，页面与实际合并结果可能矛盾；自动合并同样需要覆盖。
- 证据：[第一阶段报告](审批规则可行性验收报告.md)、`审批规则验收证据/汇总.json`、`scripts/approval-feasibility.py`。五种合并方式共 25 个用例，其中 10 个复现本问题。
- 后续方向：研究审批变更与最终合并授权的共同先后边界；参考 GitLab [问题 604469](https://gitlab.com/gitlab-org/gitlab/-/issues/604469) 和[修复 243660](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/243660)。必须先验证官方版本和功能开关，不宣称当前已对齐。
- 关闭条件：明确并发语义；撤回先完成时阻断，最终合并先取得授权时撤回不得虚假成功；验证组资格变更的生效边界。通过五种合并方式、网页/API/自动合并、受控两种执行顺序及实际 Git 引用回归。增加查询次数或修改测试预期不能单独关闭。

## APR-COUNT-002：迟到的普通推送事件错误取消新提交的批准

- 级别：P2；状态：已修复普通推送路径，真实回归通过。
- 触发：提交更新后，审批人已对新 SHA 批准，原生异步 `pull_push` 事件随后才写入时间线；旧实现用事件 ID 一律作废此前批准，导致合格的新审批被误删。
- 首次证据：`work/审批可行性-20260913-161638-081a1261/可行性结果.json` 及同目录《首次失败原生只读取证.json》，PR 15 的事件 70、71 是新 SHA 的批准，72 才是普通推送通知。
- 修复：普通推送通过审批 SHA 判定有效性；强推和目标分支变更仍保留事件边界，不删除 A→B→A 原断言。
- 回归：`work/审批可行性-20260913-164456-cabf87ee/可行性结果.json` 的“生命周期05-新提交”通过；自动化新增迟到事件固定样本及损坏事件拒绝断言。
- 边界：本修复不关闭 APR-RACE-001，也不代表强推与异步事件的全部竞态已验收。

## APR-API-003：原生时间线分页语义导致多页审批被阻断

- 级别：P2；状态：修复已接入开发代码，错误合并用例已回归通过，完整回归及只读连接边界验收尚未完成；暂不关闭。
- 触发：PR 时间线超过一页。官方 1.26.4 时间线接口的 `X-Total-Count` 是当前可见页的条数；现有通用分页器按完整总数校验，第二页少于第一页时拒绝计算。
- 首次证据：`work/审批可行性-20260913-161638-081a1261/可行性结果.json` 及同目录《首次失败原生只读取证.json》。54 条审批的原生审批列表总数为 54，时间线两页的响应头却分别为 50 和 6。
- 再现：`work/审批可行性-20260913-164456-cabf87ee/可行性结果.json`，“生命周期06-多页”仍失败。
- 错误合并首次证据：`work/审批可行性-20260913-170358-7f8a87cb/可行性结果.json`。PR 3 插入 100 条行内评论后执行 A→B→A，原生时间线三页可见数为 5、0、2。强推事件位于第三页，旧实现只读第一页，误算三票通过；实际 API 返回 200，目标引用从 `792dd52bdb403b73a156f7f30b4ca041bfac5fce` 变为 `b0284109f902f1cebc739ee006cdbba20f3f4a14`。原始“应拒绝合并”断言保持失败。
- 实际影响更新：除了误拒绝合法 PR，已进一步复现漏读强推事件后错误复用旧批准。不是 APR-RACE-001 的最终检查后窗口，未获得暂缓豁免。
- 不能采用的修改：直接忽略总数并在空页或短页结束。原生接口先分页、后过滤行内评论及不可见引用；中间页可能为空，后面仍有决定审批失效的强推事件。
- 修复验收：必须验证普通多页、整页行内评论、不可见跨库引用、页间新增/删除、晚到强推事件和 A→B→A；读取完整性无法证明时继续拒绝，不能以弱化断言换取通过。
- 当前修复：通过 Manager 既有运维连接，以 PostgreSQL 强制只读事务获得事件 ID、类型、原始排序位置和数量；按原生 API 获取审批及事件正文，并核对前后标记。只读查询设置一秒语句超时及一百毫秒锁等待上限，原始记录最多五千条，超限拒绝。
- 错库保护：数据库名称、用户及 DNS 必须对应指定容器；同时核对 Gitea web 进程持有的 TCP 连接与 PostgreSQL 实际会话。Gitea 启动时会保存新生成的内部密钥，不能把 app.ini 修改时间当作数据库身份依据。连接或权限不满足时停止，不新增权限、不改原生配置、不重启实例。
- 实际回归证据：`work/审批可行性-20260913-172309-90d3cbbd/可行性结果.json`，保留相同“应拒绝合并”断言，原生 API 合并被拒绝且目标引用保持。完整性算法八项与定位适配七项专项自动化通过；这不等于完整矩阵已通过。
- 支持边界：目前只读连接适配 PostgreSQL；其他数据库类型不能宣称已支持。真实远程 SSH 读取、故障、负载及现有实例配置边界仍需逐项验收。

- 源码依据：[官方时间线接口](https://github.com/go-gitea/gitea/blob/v1.26.4/routers/api/v1/repo/issue_comment.go)。只读核验补充路径已在隔离 PostgreSQL 验证原理，正在开发及回归；尚未向任何生产数据库增加连接或执行查询。新增时间线校验器自动化通过不等于错误合并用例已经修复验收。

## APR-CAP-005：展示读取重复计算及原生整页渲染造成排队超时

- 级别：P2；状态：已复现，正在修复和回归，未关闭。
- 首次证据：`work/审批可行性-20260913-180226-fd180b43/可行性结果.json`。隔离 Manager 1 CPU/512 MiB、Gitea 1 CPU/768 MiB、PostgreSQL 0.5 CPU/256 MiB；50 个独立登录身份同时读取同一 PR，4 个成功、46 个在 12 秒超时。两个同步 Manager 工作进程对每个展示请求重复核验原生完整状态。
- 第一次修改：仅展示路径通过 Manager 数据库合并同一 PR 的读取，两秒内复用快照；最多 4,096 行，每行不超过 64 KiB，租约和等待有上限，不保存 Cookie 或查看者身份。合并门禁不使用此缓存。复测 `180930-4a3bee4f` 为 24/50 成功，仍失败。
- 第二次修改：独立展示进程与管理、Hook 分开处理。复测 `181303-9a3ed7ae` 暴露原生整页渲染瓶颈：50 个请求中 41 个原生会话核验超时、9 个请求超时。原生 PR 页面在并发下多次耗时超过三秒，不能只增加并发线程冒充修复。
- 当前修改：Cookie 权限由原生 `pulls/{number}/info` 核验；原生个人设置页中的组件身份标记确认登录人。身份和权限仍逐请求验证，缓存最多两秒，只复用审批展示内容并保留核对时间；完整计算核验代码，浏览器继续匹配页面 head，合并不读取此缓存。正在进行真实回归。
- 容量边界：本机共享资源不等于生产硬件。以上失败足以阻止当前候选宣称支持 500/1,000 用户；未取得独立测试资源和通过证据前，不关闭容量缺口。
- 后续诊断及预算修复：r5 在两核 PostgreSQL 的 200 人突发仍有 125 次超时，四核资源反证仍有 16 次超时，原证据不变。r6 修复等待后重新计时及提交跨期快照复用，最终镜像 292 项后端回归通过；这不是 200 人容量通过，APR-CAP-005 保持开放。详见《审批展示预算修复报告》及包旁实际复验记录。
