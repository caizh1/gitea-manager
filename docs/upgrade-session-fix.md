# 升级期间会话表变化修复

版本：manager-review-parameters-20261014-r2。

## 原因

维护窗口允许 `/api/session` 返回健康状态。原认证加载函数即使在维护期间，仍会读取登录 Cookie、更新 `access_sessions.last_seen_at` 并提交；目录账号还可能刷新目录身份与复核时间。此外，原升级顺序先在暂停状态下备份，再优雅停止旧服务；停机时已进入的会话请求仍可能提交。两处写入都可能发生在升级快照之后，导致严格历史数据核对失败并触发回退。

此前隔离升级样本使用尚无个人会话表记录的旧版共享登录，没有覆盖已有个人登录 Cookie 的重复升级场景。本次补充真实个人登录、持续 HTTP 会话轮询和升级链路验收。

## 修复

在共享会话加载入口检查现有维护标记，维护期间在任何数据库和目录身份访问之前返回匿名状态。保留会话查询 HTTP 200 健康检查；不撤销或清除原 Cookie。维护结束后仍按原有过期、撤销、账号版本和目录约束认证。

升级顺序调整为：冻结并核对在途任务、固定新旧容器配置、完全停止旧服务、离线备份数据库和旧镜像、设置维护标记、启动并验证新版本。旧服务停机时完成的写入会进入离线快照。停止或备份阶段失败时恢复原容器，保留尚未被新版本修改的原数据，不使用未完成的备份；新版本启动后的失败仍按完整备份回退。

没有跳过 `access_sessions` 或忽略时间字段，历史数据库、账号、会话和密钥继续严格核对。r1 的模型采样与工具选择修复全部保留。

## 验证

认证回归覆盖本地账号的反复会话查询、维护结束后原 Cookie 恢复，以及到期需要目录复核的账号在维护期间不触发目录请求、不修改账号和会话记录。独立 Docker Compose 样本使用 r1 镜像创建真实个人登录，持续访问会话接口，再分别验证旧包故障和 r2 最终包升级。

模型服务真实审查效果仍需在用户内网部署后验证，本修复针对升级维护窗口的会话写入。
