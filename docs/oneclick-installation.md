# Ubuntu 24.04 amd64 离线一键安装

分别解压 Gitea 增强版和 Manager 安装包到永久目录，在各自目录运行：

```bash
sudo bash install.sh
```

Gitea 输入客户端可访问的 IP 或域名、HTTP 端口、Git SSH 端口；Manager 输入地址、HTTP 端口。其余密码、密钥、数据库和后台服务自动配置。包内包含 Ubuntu 依赖与固定 amd64 镜像，安装时不联网拉取。

安装完成后打开终端显示的地址。初始账号及密码位于该安装目录的 `state/access.txt`：

```bash
sudo cat state/access.txt
```

不要把整个已安装目录复制给排查人员；其中含有密码和管理私钥。故障时只提供终端指出的诊断包。

## 在页面添加 Gitea

### 同一台宿主机

登录 Manager，进入“服务器管理 → 添加服务器”，选择“本机 Gitea”。页面自动发现本机 Gitea 与其 PostgreSQL 关联实例；多实例时选择对应端口，点击“连接并添加服务器”。无需 SSH、复制管理员密码或手动生成 API Token。

管理地址按实例配置读取；若客户端实际使用其他访问地址，可在向导中填写。不要把 Git SSH 端口当作系统 SSH 端口。

### 不同宿主机

选择“跨主机 Gitea”，复制或下载页面提供的公钥。请目标宿主机管理员将公钥追加到管理账号的 `~/.ssh/authorized_keys`，目录权限为 700、文件权限为 600。该账号需要能直接执行 Docker 命令，并操作备份临时文件。

这是跨主机唯一需要目标管理员事先完成的授权步骤。然后在页面填写宿主机地址、系统 SSH 端口和管理账号，核对并确认主机指纹，发现实例并添加。私钥由安装器生成 RSA 3072 后持久保存，页面不会显示或下载私钥。指纹变化会阻止连接，不能直接忽略警告覆盖。

## CPU 兼容和 AI 状态

安装器实际执行 OpenCode 1.18.7 的版本、启动和会话接口检查，每阶段最多 30 秒；非法指令、Bun 崩溃或超时会验证 1.1.51 baseline 兼容版。CPU 指令集仅用于诊断，以真实执行结果选择镜像。

正式服务启动仍失败时也会保存原因并处理兼容回退。两套均不可用时，核心管理与备份安装完成，AI 明确停用。页面显示当前执行器健康状态；长任务不会阻塞健康刷新。安装器不会在审查任务运行中自动更换镜像。

模型服务通过 AI 页面另行配置。执行器就绪不等于模型已经配置，更不代表模型审查质量已验收。外部 Sentinel 集成默认关闭。

## 备份和恢复

备份下载是真正的 ZIP 文件，并记录文件大小与 SHA-256。恢复先校验文件和空间，保存原数据库与文件回退点，再切换数据；目标实例恢复锁覆盖验证与回退全过程。只有健康、提交一致性和事务收尾完成后才报告成功。

新 Gitea 包将数据加密密钥保存到数据卷，备份恢复同步迁移该密钥，以保留双因素认证等加密数据。恢复时保留目标地址与数据库连接配置。旧部署若仍使用环境变量固定 `SECRET_KEY`，或备份引用了无法取得的外置密钥，会在修改数据前拒绝恢复；本次不提供旧部署迁移。

## 自动诊断

从 Shell 入口开始记录，Python、Docker 尚未就绪时也有日志。终端显示当前阶段和等待上限，不需要再执行一组采集命令。

每次运行独立保存到 `state/diagnostics/<运行编号>/`，包含摘要、步骤事件、主机和容器状态、运行时探测与受限日志。失败会直接打印错误编号、失败阶段和 `diagnostics-<运行编号>.tar.gz` 路径；成功、回退与降级也保存报告。

Manager“服务器接入与诊断”页面可以查看安装与运行诊断、步骤详情及下载包。连接、备份、恢复通过同一个操作编号关联错误。未知原因明确标记为未确定，不把 CPU、杀毒软件等猜测当作根因。

日志写入前脱敏，不导出完整环境变量、配置文件、私钥、Token 或仓库源码。单个日志源最多 2 MiB，每次最多 20 MiB，保留最近 10 次且总量最多 200 MiB；诊断目录和文件分别为 0700、0600。附加诊断有 30 秒总预算，采集失败不能覆盖主错误或阻止恢复回退。

## 重跑、重启与边界

同一目录重跑保留原账号、密钥、执行器选择和数据；容器重建、系统重启继续使用持久卷。保留 `state/` 和 `compose.install.json`。不要删除状态来强制重新初始化。Manager 重装不删除 Gitea；本入口不用于升级或迁移旧 Manager。

全新 Docker 在导入镜像前配置 overlay2；已有 Docker 不自动切换存储驱动或重启，先进行镜像创建与启动预检。已有非 Ubuntu Docker 若缺少兼容 Compose，会说明原因并停止，不替换运行时。

支持 Ubuntu 24.04 amd64、systemd、root、标准 Docker socket。建议 Manager 至少 4 GiB 内存，Gitea 与 PostgreSQL 至少 2 GiB；预留安装目录及 Docker 数据目录空间。默认内网 HTTP；Manager 目录登录、会话及目录配置保存要求 HTTPS。Manager 包附带 `organization-access-ldap.md`，说明企业证书安装参数、Gitea 字段对照和升级回退；客户端 CA 信任、防火墙和 DNS 需按实际网络配置。

## 构建与校验

联网准备机使用固定基础镜像、OpenCode 归档校验值和离线依赖。构建入口为 `deployment/build-v2.py`，打包入口为 `deployment/build-installers.py`；前端先执行 `npm run build`。构建输入记录在包内 `build-provenance/`，依赖版本在 `runtime/debs/package-versions.txt`。

每个安装包附有 `.sha256`，包内 `SHA256SUMS` 在安装前自动核对。最终验收状态、已验证范围和未验证项见交付验收报告；候选包与历史验收记录不能替代最终报告。

## 首次安装失败后清空重装

在对应安装目录执行 `sudo bash uninstall.sh`。先核对终端列出的产品、实例和资源，第一次输入 `UNINSTALL`，第二次完整输入终端显示的 `DELETE 实例编号`。任何其他输入或中断都会取消后续删除；已经执行的删除无法撤销。

卸载永久删除当前实例的数据卷、容器、网络、安装状态和凭据。Gitea 的仓库及数据库会全部清空。Manager 的数据与密钥会清空，但不删除其他 Gitea 实例。该脚本仅用于首次安装失败恢复；Manager 已有服务器、备份、恢复或调度记录时拒绝卸载，避免中断对 Gitea 的管理任务。清理失败时保留剩余状态及错误报告，可以排除原因后重新运行。

Docker、共享镜像、离线包及安装脚本保留，可再次执行 `sudo bash install.sh`。不含业务数据和密钥的卸载诊断保存在 `uninstall-diagnostics/`。不要把卸载作为生产数据备份或常规升级手段。

### 用新包自动卸载旧实例

在新解压包的对应产品目录执行 `sudo bash uninstall.sh` 即可，不需要输入或查找旧包路径。脚本先读取本机 Docker 的 Compose 项目标签、端口和原工作目录，再自动核对原安装身份：只有一个同产品实例时自动选中，存在多个实例时显示端口及实例编号供选择。若当前目录本身对应一个仍存在的实例，则优先处理本实例。

选中后展示确切容器、数据卷和网络，仍需两次确认。卸载会清理自动定位的原安装状态与凭据，新解压包不删除。缺少可核验身份、找不到资源或存在残留时明确失败，不再将“没有执行删除”报告为卸载成功。仅名称相似但无法证明归属的容器不会自动删除。
