## 实现与实际执行

新增 `scripts/approval-feasibility.py`：创建独立官方实例，生成真实组织、团队、仓库、用户和审批，安装只用于实验的同步 Hook，通过原生 REST 执行合并、撤回及组成员修改，并核验最终 Git 引用和 PR 状态。实验控制器模拟外接审批查询和判定；它不是完整生产审批服务，也不是模拟的 Gitea API。

新增《审批规则测试矩阵》：拆分生产存量接入、安装中断、回退、原有规则共存、并发、页面、权限及长期运行等测试。尚未执行的项目全部明确标记，不记入通过数。

两次完整实验覆盖五种合并方式，共 25 个真实用例：15 个正反对照符合预期，10 个严格时序用例复现同一个方案阻断。每个合并请求的执行者为普通代码写入用户 `author`，未使用管理员强制合并。管理员只在隔离样本中初始化数据和调用原生审批驳回/团队管理接口。

| 合并方式 | 正常批准 | 提前撤回 | 两次检查之间撤回 | 最终检查后撤回 | 最终检查后移出组 |
|---|---|---|---|---|---|
| merge | 正确合并 | 正确阻断 | 第二次检查阻断 | 错误合并 | 错误合并 |
| rebase | 正确合并 | 正确阻断 | 第二次检查阻断 | 错误合并 | 错误合并 |
| rebase-merge | 正确合并 | 正确阻断 | 第二次检查阻断 | 错误合并 | 错误合并 |
| squash | 正确合并 | 正确阻断 | 第二次检查阻断 | 错误合并 | 错误合并 |
| fast-forward-only | 正确合并 | 正确阻断 | 第二次检查阻断 | 错误合并 | 错误合并 |

“错误合并”是相对于本计划的严格条件：指定组资格或审批在 Git 引用更新之前已经撤销成功，新增规则已不满足，但目标分支仍写入本次合并对象。不是根据 HTTP 成功或页面提示推测。

## P0/P1 BLOCKERS

### P1：外接判定与原生审批变更缺少共同的原子边界

- **具体位置：**当前“原生审批及组成员继续独立修改，外接 Hook 通过 API 查询后放行”的设计。实验在 `scripts/approval-feasibility.py` 的 `case()` 中安排变更，并在 `install_probe()` 的最后一次 `update` 检查后暂停。官方 `services/pull/merge.go:244` 使用 PR 工作锁；官方 `services/pull/review.go:412` 的审批驳回流程没有取得同一把锁。
- **触发条件：**合并在途，外接最后一次检查已通过，但 Git 尚未更新目标引用；此时通过原生 API 成功撤回指定组唯一有效审批，或移除批准者的指定组资格。
- **完整因果链：**四名有效批准者、两个必需组各一票 → 普通用户发起合并 → pre-receive 与 update 两次读取真实审批/组状态，均通过 → 暂停最后一次检查之后的执行 → 原生撤回或组修改成功并回读，Committer1 有效票数变为零 → 确认目标 Git 引用仍为旧值 → 恢复 Hook → Git 写入 Hook 中记录的新对象，API 返回 200，PR 标记已合并。
- **实际影响：**受管目标分支包含不满足指定审批组要求的变更；自动化和并行人工操作可以触发该执行顺序。不能达到“直到 Git 写入前撤回都必须取消放行”的严格语义。
- **为什么达到 P1：**这破坏该功能最核心的强制审批正确性，涉及所有已测合并方式，且不能通过页面提示或事后回滚恢复为“从未错误合入”。本级别按用户批准的严格时序要求评定，不代表现有 Manager 已有一个上线漏洞，也不是对原生 Gitea 安全漏洞的声明。
- **支持证据：**`审批规则验收证据/汇总.json`、`普通合并结果.json`、`其余四种合并结果.json`；其中保存每阶段有效审批、原生身份、真实 Git 输入、变更完成时刻、恢复时刻、最终引用、PR 状态和原生配置核对。
- **已完成反证：**见下一节。该结论没有把“未执行”或概率性猜测作为阻断。

## 反证检查与结论边界

1. **不是原生票数不足造成的假象。**原生保护要求三票。撤回后仍有 Bob、Carol、Dave 三票；移组后仍有四张有效原生批准。缺失的是新增要求中的 Committer1 票。
2. **不是管理员绕过。**合并者是普通代码写入用户，并且原生设置启用了禁止管理员覆盖；合并请求没有强制参数。
3. **不是空组特殊处理。**移除 Alice 后 Committer1 仍保留未批准成员 Spare，组有效但没有合格批准。
4. **不是误把安装成功当作执行成功。**真实 Git 合并执行了两个自定义 Hook，同步点保存了输入对象与原生 PR 标识；最终目标引用等于最后 Hook 记录的新对象。
5. **不是只检查一次。**提前撤回会拒绝；在 pre-receive 后撤回，update 再检查也能拒绝。问题仍会出现在最后一次检查之后，因此增加次数只移动边界，不能提供共同原子性。
6. **不是撤回发生在合并之后。**变更完成后、解除同步点之前再次读取实际 Git 引用，确认其仍为旧值；单调时钟记录了该顺序。
7. **不是模拟 API 或修改过的 Gitea。**运行官方仓库摘要固定的 1.26.4 镜像；原生规则和 Hook 包装器前后相同。两个完整实验期间 Gitea 的启动时间没有变化，实验完成后只停止自己创建的实例。
8. **同步等待的意义。**暂停用来确定性选择一个可达的并发执行顺序，不估计现实中发生概率，也不作为性能指标。操作系统调度或进程暂停同样可以分隔“最后检查”与“写入”；测试没有修改 Gitea 二进制来制造这一边界。
9. **不扩大结论。**本实验不能证明一切外接架构都不可能；它证明当前保持原生修改独立生效、仅靠 Hook/API 状态快照的架构不能满足上述严格要求。如果改成“以最后检查时点为准、之后撤回不取消已授权的在途合并”，本用例不再属于该新语义下的错误，但这是需求变更，不能静默作为修复。

## 复现与交付边界

先确保本机 Docker 中存在上述官方 Linux amd64 镜像；主机 Python 3.9 或更新版本即可，不依赖第三方 Python 包。运行：

```bash
python3 scripts/approval-feasibility.py
```

可用 `--styles merge` 只运行普通合并五个子用例。脚本不接受生产 URL、现有容器或数据卷参数。报告与一次性凭据分别放在 `work/审批可行性-<运行标识>/`，目录 0700，配置文件 0600；凭据不进入交付包。完成后停止隔离容器，保留卷用于追查，后续清理只能按本次项目及标记选择。

本次交付为源码、测试矩阵、反证结果和可行性验收包，**不是审批功能部署包**。用户要求“不能可靠阻断错误合并，就停止强制接入开发”，因此没有继续制作形式上可安装、实际不满足审批底线的组件，也没有覆盖现有 `gitea-manager.tar.gz`。

继续实施需要先解决原生审批/成员变更与实际合并的共同原子边界，或者明确调整在途合并的生效语义。仅增加轮询、重试、状态检查或展示面板不能关闭本次阻断。
