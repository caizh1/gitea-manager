## 验收边界

- 用户为仓库开发者和 Manager 管理员；输入为固定 PR 累计 diff、程序选取的上下文、人工明确确认的本仓库经验。
- 本机真实 Gitea 为官方 1.26.4，OpenCode 为 1.18.7，真实模型服务返回的模型标识为 `deepseek-flash`。只发送合成代码，没有发送公司源码。
- 内部 New API、生产 `deepseek-v4-flash`、真实 UFS 硬件及公司项目尚未验收。官网测试不能代替这些验收。
- 之前的十组样本按 SHA-256 原样冻结：每组一个缺陷 PR、一个正常对照 PR，共 20 个。没有把答案、判分依据或复现驱动提交给模型。
- 人工基线为固定源码、可执行复现和独立的因果/位置复核；没有人工工时基线，不能宣称节省 80%。目标是保留有效建议、可靠定位以及减少重复人工纠正；不能据本批样本宣称普遍零误报或零漏报。

## 因果链人工复核

位置正确不等于全部解释正确，以下问题均保留原始输出：

1. mapping_flush 根因正确，但“没有任何方式恢复 dirty / 永久丢失”过度确定；后续 map_update 可重新置 dirty。已保存“部分错误”纠正。
2. erase_pool 根因正确，但模型举例先 pool_seed 再 erase_begin，此路径被入口 free 检查拒绝；有效复现是 pool_init → erase_begin → 完成前分配。block_retire 可回收状态，不能直接认定永久泄漏。已保存“部分错误”。
3. map_page 的映射错乱正确，但模型把越界解释为内层 slot+i 超界；n 已受 ENTRIES-slot 限制，内层不会因此越界。跨多页浪费容量后可能越过外层 page，需另外说明触发条件。已保存“部分错误”。
4. erase_pool 日志值没有被定义为成功计数，也没有控制消费者；原日志建议缺少充分依据。通过开发者命令保存条件化排除，保留真实 free 状态问题。
5. split_complete 正文正确描述剩余一个请求即提前完成，但标题“最后一个子请求完成时提前”不精确。

十个根因均有真实源码和复现支持；完整解释准确度低于根因检出率。不能把“10 个都报出”写成所有自然语言判断都正确。

## 首次异常与证据

一次候选包验收中，自然语言缺少 support/trace 的行内发布通过，但后续字面量返回的反馈关联失败。新增的函数名称兼容分支只接受简写，未接受解析器的完整声明；已恢复原有声明提取并兼容简写，回归改为真实解析器输出，176 项重新通过。失败包不作为最终交付包，失败证据保留，修正包在另一个全新卷实例重新验收。

Docker 虚拟机约 7.7 GiB，曾同时运行多套历史验收栈；新增离线环境后发生全局 OOM，执行器三次退出 -9，当前测试 Gitea 也被终止，造成 12 个任务失败。保留原失败任务与资源证据，确认六套旧验收环境无在途任务后仅停止容器、保留卷，再恢复当前测试 Gitea。没有重写失败结果，也没有升级用户手测环境。资源恢复后的 12 个新 PR 全部成功。

详细清单位于交付的 `outputs/审查数据集与十场景复测-20260912/`：`PR清单.json`、`定位与指标核验.json`、`经验迁移核验.json`、`原始证据/`、`经验迁移原始证据/`、`页面证据/`、人工标注与导出记录。它们与源码和说明分开提供，运行密钥和数据库不进入离线包。
