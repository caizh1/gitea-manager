# AI Review 人工反馈与经验数据集

本功能服务于仓库开发者与 Manager 管理员：保留开发者对 AI 的纠正，也保留人工发现的真实缺陷，为同仓库后续审查提供少量相关参考。它不是自动训练模型，不保证模型从此不再犯同类错误。

## 辅助意见发布

分析版本升级为 3。具体问题和自然语言原因是必要输入；support、trace、修改前后行为等辅助字段不再单独决定是否发布。候选的反证响应缺失或格式不完整时，保留原始候选并标记「待开发者确认」，缺少可用问题与原因的输出仍报错。已有保护足以排除、问题不可达或未由本次修改引入等有实质理由的反证，仍可排除候选。

行内位置校验保持独立：固定提交、文件、修改侧、diff 锚点、精确原文、根因语法操作及两次定位判断都要一致。缺少 support 中重复的根因引用不再单独降级。无法可靠定位仍作为普通意见，不猜行号。历史任务保留旧协议，不补发旧结果。发布中的瞬时 Push 竞争仍是此前明确接受的限制。

## 开发者操作

在 PR 对话中单独提交一条命令；每条已发布的新协议意见显示 AR- 开头的意见编号。

```text
/ai-review 反馈 AR-意见编号 误报 具体原因
/ai-review 反馈 AR-意见编号 排除 具体原因 条件=明确的适用范围
/ai-review 反馈 AR-意见编号 部分错误 纠正错误的因果或影响
/ai-review 反馈 AR-意见编号 定位错误 正确位置和原因
/ai-review 反馈 AR-意见编号 有效
/ai-review 反馈 AR-意见编号 撤销
```

「有效」可以不补充原因；其他标注应说明原因。排除必须写明 `条件=`，不能把「以后不要再报」当作通用规则。内容太少会保存为待补充。相同作者后续反馈替代其旧标注；不同作者对同一来源给出不同判断，记录冲突，暂停相关样本参考。

人工普通评论和已正式提交的行内 Review 会先保存为候选。用下面命令明确确认：

```text
/ai-review 收录 当前PR评论链接 触发条件、原因和实际影响
```

行内新侧评论可从所属 Review 固定 SHA 读取上下文。普通评论无法可靠还原创建时的代码版本，旧侧评论也不能使用当前 base 猜测历史版本；此时保存为待补充，可在确认命令中补充：

```text
/ai-review 收录 当前PR评论链接 触发条件、原因和影响 版本=完整40位SHA 文件=仓库相对路径
```

SHA 必须属于当前 PR 的提交集合。带空格的路径用双引号包裹。补充文件最多 12000 字。可选 `修复=完整SHA` 关联当前仓库的修复提交和补丁，系统不据此自动认定修复已经正确或测试通过。

撤销自己确认的人工样本使用 `/ai-review 反馈 DS-样本编号 撤销`。编辑或删除来源及确认评论会使旧确认失效，需要重新说明；管理员停用不能被新的评论事件自动恢复。原始意见、人工纠正和每次修订分开保留，不删除开发者讨论。

命令只接受当前仓库具备代码写权限的真实 Gitea 用户。服务端重新查询用户 ID、账户状态和仓库权限；组织分单元团队另核对 repo.code 写权限和成员身份，不能用 PR 写权限替代。只读或停用成员的反馈不会进入生效数据集。人工评论作者可以是只读审查者，但确认者须有写权限。链接只允许当前仓库、当前 PR、同一 Gitea 的已验证入口，不会跟随用户提供的链接发起网络请求。

## Manager 与持久化

AI Code Review 页面新增「审查经验数据集」，可按仓库、状态筛选，查看原文、纠正、固定版本和最近 100 个不可变修订，停用样本并下载 JSONL 数据集 ZIP。导出包含格式说明、样本数及 JSONL 的 SHA-256；历史导出包含所有状态的修订。单次历史导出最多 10000 条或 32 MB。

数据集存入现有独立 Review SQLite 的专用表，与任务快照的 30 天清理分离。正式发布成功后，由反馈进程异步归档必要代码与模型版本。反馈归档失败不改变已完成的正式 Review；尚未成功归档的任务不会被清理掉。原始模型密钥、机器人 Token、管理凭据不进入数据集。

## 生效范围与失效

每个分析单元最多采用三个样本，总长度不超过 2000 字，且不挤占当前源码的输入上限。使用确定性文件/操作符号关联，不做全库模糊搜索，不使用外部向量库。任务开始时冻结候选修订；实际传入的样本 ID、修订与内容存入任务证据，详情可查看。历史锚点和旧行号不会进入新任务的发布定位。

模型需要依据当前代码重新判断。人工正例不是当前缺陷的证据；排除条件不能抹掉条件不成立时的真实问题。未经确认、冲突、撤销、停用、来源有效期过期的样本不提供给模型。反馈进程定期补偿核查来源和写权限，五分钟内未能重新核查的样本停止参考；已开始的任务保留其冻结参考记录，不自动重审。

仅采集安装新版 Webhook 后发生的评论活动。重装已有 Webhook 保留启用时间，不批量导入旧讨论。Gitea 的正式 Review 通知没有评论 ID，反馈进程按 PR 回读已提交评论集合；不会把未提交草稿当成人工确认。

## 部署与升级

新增 `review-feedback` 独立服务，复用后端镜像，读写 Review SQLite，只读挂载 Manager 数据目录以读取对应服务器的权限核验凭据。它不挂载 Docker socket、SSH 密钥或执行器凭据，不接入模型执行网络，不调用模型。Worker 和模型执行器仍无法访问 Manager 数据库。

生产叠加配置：`compose.ai-review.yml` 与 `compose.ai-review.images.yml` 已包含该服务；本机独立配置为 `compose.review-local.yml`。自定义 Manager 数据卷时，需要把 feedback 的 `/app/data:ro` 挂载调整为同一个数据卷。数据库和锁文件继续使用 Linux 原生持久卷。主密钥通过既有部署秘密提供。

升级 Manager、Worker、进度服务和前端后启动 feedback；等待在途审查完成再替换 Worker。随后在 Manager 仓库管理中重新安装/核对事件通知，新增 PR 评论与人工 Review 通知。Gitea 1.26.4 注册事件使用 `pull_request_review` 分组，投递使用具体事件类型；服务同时校验 HMAC、真实仓库和 PR 归属。

管理接口沿用登录、同源检查与写入 CSRF：

- GET `/api/ai-review/repositories/<id>/dataset`
- GET `/api/ai-review/repositories/<id>/dataset/<样本ID>/history`
- POST `/api/ai-review/repositories/<id>/dataset/<样本ID>/disable`
- GET `/api/ai-review/repositories/<id>/dataset/export?history=1`

全部运行依赖沿用现有离线 wheel、固定 OpenCode 与镜像。全局默认关闭，没有新增合并门禁。样本质量需按实际内网模型和真实项目持续验收；没有人工计时基线，不能宣称节省 80% 人工。
