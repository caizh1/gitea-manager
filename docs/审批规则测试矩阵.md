> 2026-09-13 后续决策：允许继续功能开发及隔离测试；最终检查后的撤回/移组竞态记录为 APR-RACE-001（P2、已知失败、暂缓修复）。保留下列原始断言和首次结果，不从必测统计中删除。新增执行结果单独记录，历史“停止”描述不代表当前开发状态。正式强制发布仍受[发布门禁](审批规则缺陷与发布门禁.md)约束。

适用边界：官方 Linux amd64 镜像；扩展不修改 Gitea 源码、数据库结构、原生规则或历史数据。原生规则与新增规则同时生效。存量 PR 保持原流程，仅切换后新 PR 使用新增规则。初始目标为总票数至少三人、Committer1 和 Committer2 各至少一票，跨组用户总票数去重。

## 一、可行性反证（已实现独立运行工具）

工具：`scripts/approval-feasibility.py`。每次创建新项目、新网络和新卷，只向随机回环端口提供访问，不接受已有实例地址。试验完成或异常后停止自己的容器，保留第一次失败及证据，不重试业务写请求。程序退出码 2 表示发现方案阻断，不能解释为测试工具崩溃。

| 子用例 | 操作 | 必须核对的证据 | 执行状态 |
|---|---|---|---|
| 可行性-正常 | 四名有效批准者，两个必需组各有一票，以非管理员作者合并 | 原生要求三票；实际 Git 引用更新；PR 已合并 | 见可行性验收报告 |
| 可行性-提前撤回 | 请求合并前撤回 Committer1 唯一有效批准，保留原生所需三票 | 自定义检查拒绝；Git 引用不变；PR 未合并 | 见可行性验收报告 |
| 可行性-中间撤回 | pre-receive 通过后撤回唯一组票；update 再次读取审批 | 第二次检查拒绝；排除“再加一次检查即可彻底解决”的混淆 | 见可行性验收报告 |
| 可行性-最终撤回 | 两个阶段都通过后，暂停 update；原生撤回成功并回读后再恢复 | 撤回时 Git 尚未写入；最终引用与 Hook 输入一致；记录是否错误合并 | 见可行性验收报告 |
| 可行性-最终移组 | 两个阶段都通过后移除已批准者的指定组资格；组内仍有未批准成员 | 成员修改已完成、组票为零、原生四票仍有效、最终实际写入结果 | 见可行性验收报告 |

每种子用例分别运行 merge、rebase、rebase-merge、squash、fast-forward-only，共 25 个真实实例用例。网页和自动合并入口不因 API 路径结果而标记通过。原生 Hook 包装器及分支规则前后必须一致。

## 四、性能、证据与发布判定

- 影子和未受管业务：原业务零新增失败、连接不中断、主进程和容器不重启；端到端 P95 延迟回归不超过 5%，同时满足现场原有服务指标。
- 强制门禁：P95 不超过 3 秒，硬超时 10 秒。上述反证工具的同步等待用于构造时序，不能作为生产性能测试。
- 影子和强制模式各运行 24 小时；分别覆盖常态、实际峰值和两倍峰值。现按用户提供的千人研发规模建立 500 活跃用户峰值、1,000 两倍压力档，见《审批规则容量验收基线》。这是估算负载；未取得真实现场峰值时，现场容量指标仍未验证。
- 每个结果包含用例编号、前置数据、操作、预期、实际、镜像与脚本摘要、证据路径、首次失败以及修复后回归结果。
- P0/P1/P2 未关闭、必测项未执行/跳过/失败或无证据，均阻止发布。代码覆盖率、HTTP 成功或安装器退出码不能替代真实 Git/PR 验证。
- 历史阶段决策保留：“第一阶段失败后，不交付强制审批部署组件，不启动后续生产接入或后台长测”；具体首次结论见《审批规则可行性验收报告》。当前用户已允许继续开发和隔离测试，可交付带发布阻断的隔离候选组件；没有授权带未关闭缺陷正式强制接入生产，也没有改变原始失败断言。
