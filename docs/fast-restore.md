# 备机快速恢复

在定时任务中选择快速恢复备机。Manager 将该源站最近七个成功备份点预传到指定备机，并在备机上核对归档大小和 SHA-256。备份和恢复页面提供独立的预传进度及结果。预传包含全量数据、仓库、数据库和 Actions 制品。源端早已缺失的制品继续记录告警。

Manager 的备份目录仍存放可单独恢复的标准 ZIP。备机缓存使用目标 Docker 引擎上的独立卷，恢复时只读挂载。预传不停止正在运行的备机。已连接的备机有短暂积压时，接收端会短等分块送达。长时间无进展时，Manager 继续完成独立备份。备机副本已有接收进度时会等待接续，避免同时重发整份数据。点击恢复时，目标端从本机缓存解包并校验文件，准备好文件和数据库后才停止服务。现有的密钥、数据库、Git 引用、Actions 文件和业务健康检查均参与发布条件。缓存缺失或校验异常时可使用 Manager 的独立全量 ZIP。

备机长期保留七份，30 GB 样本约需要 210 GB。第八份生成期间另需预传、合并、解压及数据库回退空间。同一个 Docker 卷存储所在磁盘建议给七份样本留出至少 300 GB，另加已有业务数据和回退占用。配置生效后的首个备份优先补齐。已就绪副本在运行中的恢复和新一份核验完成前保留。

按需启用「跨夜内容复用」。此选项适用于该源站的备份，在源站恢复服务后才读取只读固定副本。Manager 使用长度和 SHA-256 核对上一份本地全量 ZIP 或分块缓存，下载缺失或损坏的分块，重建并核对源端整份归档，再生成当天标准全量 ZIP。Manager 需要额外缓存上一批已核验分块和正在接收的分块。首次向空 Manager 发送 30 GB，即使一直跑满 2 MB/s，至少需要 4 小时 10 分。后续发送量取决于仓库、LFS、制品和 ZIP 的实际变化。

## 验收方法

使用 Windows 实验机上的隔离 Linux 环境和两个独立 Docker 引擎。仅对源站到 Manager 限速 2 MB/s。记录两个链路分别及并发传输时的实测吞吐。保留相同 30 GB 样本的普通恢复基线。

用同一套真实 API 创建八个停写点，完成第八份自动恢复，再断开源站依次恢复最近七份。核对当前快照的 Git 引用、对象、数据库、LFS、附件和所有 Actions 制品。自动恢复从 Manager 确认全量 ZIP 的时间开始计时，手动恢复从请求开始计时，另记目标实际停服时间。七份均在 15 分钟内恢复且全部数据校验通过，才可判定达到目标。验收入口为 `scripts/backup-fast-restore-acceptance.py`。
