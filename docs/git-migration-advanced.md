# 高级迁移完整基准验收

## 结论与范围

本轮补齐跨仓库合并请求、非通用制品、项目级复杂规则和 CI 历史的迁移链路。真实 GitLab CE 16.1 与 Gitea 1.26.4 作为来源，配套增强版作为接收端，分别通过 Manager 接口、独立 Worker、原生接收、最终群组交接和消费端验收。所有实例均为带测试标记的独立容器与卷。

目标用户为平台迁移管理员。输入为来源专用迁移管理员、目标管理员连接、已有目标群组、已有账号的规则主体映射，以及覆盖全部依赖仓库的停写确认。只选择一个业务仓库时，系统自动固定跨仓库请求涉及的依赖闭包，并迁移全部依赖；本地限制为每批最多一百个项目。

人工基线是逐仓导出 Git／Wiki、整理原生资料、逐文件上传下载、重建规则和人工核对。本轮量化指标为支持范围内的清单覆盖率、字节摘要差异、实际允许与拒绝行为，以及自动执行区间。没有进行真实公司项目的人工对照计时，人工节省百分之八十仍为未验证，不能根据自动化程度推算已达成。

## 整批结果

以下是完整固定基准，所有盘点到的对象／引用回执和文件均核对，没有用单个成功样本代替其余清单。

| 来源 | 依赖闭包仓库 | 对象／引用回执 | 文件 | 原生制品协议 | 真实规则场景 | 下载后执行的 C 产物 |
|---|---:|---:|---:|---:|---:|---:|
| Gitea 1.26.4 | 2／2 | 32／32 | 22／22 | 5／5 | 10／10 | 2／2 |
| GitLab CE 16.1 | 2／2 | 22／22 | 17／17 | 5／5 | 13／13 | 2／2 |

- 三十九份文件全部重新下载，大小和 SHA-256 与固定来源回执一致。比较范围内字节差异为零；这些指标不代表未纳入基准的格式或版本。
- 两条开放的跨仓库请求均通过原生合并接口实际合并，并回读确认。来源仓库编号指向迁入的依赖仓库，没有替换为同仓分支。依赖仓库当前作为独立仓库导入，不重建整个 Fork 网络。
- 两类来源分别在写入期间停止 Worker，再从同一任务与仓库编号恢复成功；维护期间重启 Worker，迁移数据库摘要保持不变。
- 最终一轮任务从创建到完成约为一分钟级别，包含人为中断恢复；精确创建、开始和完成时间保存在原始执行证据中，不作为人工效率对照。
- 最终迁移执行期间没有逐项手工补写业务数据。夹具搭建及本机高负载下的一次启动重试属于测试准备，不能隐藏为零人工成本。

## 四类功能

### 跨仓库请求

自动递归发现来源项目，固定依赖图，先建立所有仓库与代码，再导入真实来源仓库关系。循环依赖去重，不可读或已删除的依赖明确阻断。接收端要求相同管理员、相同批次、仍处于装载状态的私有隔离会话；不能关联外来仓库。最终路径变更后保留稳定仓库编号，并实际检验合并。

首个推送只包含来源默认分支，等待原生仓库确认非空后再发送其余引用。清理临时引用前同时核对数据库默认分支与实际 Git HEAD，避免异步回调把临时传输分支选成默认分支。失败检查点和早期失败容器均保留。

### 制品

本轮新增 npm、Maven、PyPI、NuGet 和 Helm，保留已有通用包。通过原生索引、清单和下载协议逐个消费全部文件，npm 包覆盖两个历史版本，核对 npm 依赖／运行时约束／源端实际分发标签、PyPI 解释器约束、NuGet 依赖与生成清单、Maven 文件及 Helm 索引。PyPI 连续分隔符名称按同一等价规则规范化。npm 注册表的版本元数据优先于归档字段，保留来源实际的说明与依赖；固定基准特意设置注册表依赖为第三版、归档依赖为第二版，并验证迁后仍采用源注册表的第三版。多个版本的索引只读取一次，避免重复读取同一完整版本表。

部分旧 GitLab 协议没有 SHA-256。盘点时读取正文固定 SHA-256，核对已有 SHA-1／MD5；执行和最终来源检查继续比较正文摘要，不能把缺少摘要当作空包或成功。NuGet 清单与接收端生成文件重名时，仅在本会话且字节完全一致时复用，不覆盖其他文件或外来同名包。

OCI／容器镜像按用户最新要求暂不包含。Composer、Conan、Debian、RPM、RubyGems 等其他协议未宣称支持；被盘点到但不能迁移时仍会阻断交接。

### 规则

覆盖未来分支的大小写敏感模式、GitLab 重叠模式的最宽授权合并、Nobody 推送／合并、强推、Gitea 原生优先级和标签保护。使用实际 Git 推送验证允许与拒绝；拒绝必须具有明确的保护或权限原因，断线和其他网络错误不能计为拒绝通过。

GitLab 标签分别保存创建主体与删除维护者，禁止通过 Git 改写和删除受保护标签；维护者可经原生接口删除，普通写入者不能删除。现存保护分支的 Nobody 合并规则同时核对来源有效身份下的拒绝和目标原生接口的拒绝。规则主体是已确认的静态账号映射，不自动同步来源成员变化。

### CI 历史

逐作业保留成功、失败、未执行及手动状态，迁移所有可读取的日志、归档、原始 JUnit、元数据索引和原始追踪文件。已擦除、已过期或仍在变化的记录明确进入缺口，不能伪造文件。未启动作业保留状态，不虚构日志。

Gitea 旧上传协议的产物不会出现在新版 REST 制品列表，因此逐流水线读取网页运行视图，补齐全部已确认文件。本基准找回四份旧协议产物，含两份 C 二进制；没有把 REST 空列表认定为没有产物。

Gitea 使用官方 act_runner 实际执行工作流。GitLab 使用真实 Runner 协议领取、上传日志／归档／原始报告，实际 C 编译与运行在隔离容器完成；不是官方 GitLab Runner 二进制的部署验收。目标迁入工作流保持关闭，不运行历史配置或历史产物；已知 C 基准只在验收侧的无网络容器中执行。

旧版网页文件需来源专用迁移管理员的可用网页登录，二次认证或令牌权限不足时明确阻断。源端最近登录时间、下载计数和异步可合并性属于派生状态；不因此误报业务变化。账号编号、提交、正文、规则及文件摘要仍严格核对。
