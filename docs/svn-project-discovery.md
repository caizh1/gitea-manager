# SVN 实例发现与项目纳管

## 使用方式

1. 添加 SVN 实例，填写名称、实例入口、账号和密码；英文标识自动生成，证书等在高级设置。
2. 点击“连接并发现项目”。实例列表读取及项目验证均在独立 SVN 执行器内只读完成。
3. 在发现的项目中单选、多选或全选；“查看目录”只读显示项目内的目录。点击“纳管所选项目”直接登记并打开迁移计划，不需要再次确认范围。
4. 选择目标 Gitea 增强版实例，保存计划并预检；完整读取和停止写入确认仍在正式执行前保留。

项目内部的 `test_spec` 等目录不作为独立项目、不默认排除。纳管本身不修改 SVN，也不会立即创建目标仓库或执行迁移。已经纳管的项目会显示状态，不重复登记。

如果实例未开放列表，使用“补充项目地址”后仍走同一套项目识别和纳管流程；认证失败显示红色错误，不能把它描述为空列表。网络、证书和权限问题需要在实际部署环境修正。

## 完整内容如何保留

新纳管记录存储完整项目模式，预检时读取实际目录。项目根部存在明确的标准主干、分支和标签时，保留它们的 Git 分支和标签映射；同时在**同一个目标仓库**增加 `svn-project` 完整项目归档分支，保留原始目录树及每次提交，包括 `test_spec` 和其他主干之外的内容。名称冲突时自动使用后缀。该分支与主干一样经过逐提交文件集合、内容、模式、作者、时间、日志和修订覆盖核验，并随其他引用推送和远端回读。

原始结构没有明确标准布局时，整个项目目录直接成为默认分支，保留原目录层级。不会凭猜测把普通子目录认成分支，也不强行扁平化原始目录。历史 SVN 空目录、属性与 Git 的表示差异沿用原报告机制；外部引用仍会阻断预检。

旧的指定布局记录不被自动改写，避免改变既有计划的范围；可以编辑仓库并选择“完整项目”升级为新模式，原预检随版本变化失效。

## 发现边界

支持 HTTP/HTTPS 目录索引中的同来源直属仓库链接（含 VisualSVN 传统列表和 Apache SVN 列表），使用现有账号逐个通过 SVN 协议验证。纯 `svn://` 服务没有通用的实例仓库枚举能力；已知项目地址仍可直接识别。现代页面若只通过不兼容的私有接口输出列表，会提供备用入口，不报告“没有仓库”。

同一个 SVN 仓库内，只有所有顶层目录都具有明确的项目主干布局，且没有其他顶层文件时，才将它们列为独立项目；否则整个登记目录保留为一个项目，避免遗漏共享目录。不会递归把 `test_spec` 等内容目录当成项目。

最多接受 256 个项目、单项目根列表 2000 项，HTTP 索引 2 MiB，总发现时间五分钟。跨来源链接及重定向被拒绝，不执行网页脚本。结果绑定来源版本；来源改动后必须重新发现。纳管使用事务与实例版本校验，失败不会只登记一部分，重复提交不会重复创建。

## 验收基线与结论边界

人工基线是逐一找到项目 URL、检查内部布局、填写路径，再逐个登记。目标用户为平台管理员，输入为可读取项目的实例账号，目标是将正常路径缩短为一次连接和一次多选提交。固定样本覆盖真实 HTTP 三仓库、共享 SVN 仓库两项目、普通额外目录、标准分支和标签、完整项目归档、认证失败与列表受限。

工程质量门槛：选中项目全部纳管，未选项目不新增；任何普通内容目录不擅自拆分或遗漏；错误发现结果自动纳管数为零；历史内容与元数据核验全部通过。实际公司 VisualSVN、Windows 域认证、生产规模与人工时间对照尚未验收，不能宣称已达到减少人工百分之八十。

设计依据为本次确认的第二版流程图，正常流程没有“确认范围”或“处理特殊目录”步骤。隔离验收与发布证据记录于 `docs/evidence/svn-project-discovery-release.json`。
