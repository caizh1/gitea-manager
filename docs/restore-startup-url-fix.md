# 恢复启动检查的无协议地址修复

日期：2026-10-13。

## 现场证据与根因

用户确认目标服务器编辑页保存的地址为 `10.10.5.21:9929`，没有协议前缀。现场诊断编号为 `20261013T110053Z-1a86ed05`，失败阶段为 `start_gitea`。

目标容器日志显示，19:05:03 启动，19:05:06 开始监听 `0.0.0.0:8929`，对外根地址为 `http://10.10.5.21:9929/`，19:07:03 收到停止信号。停止时间与启动检查的 120 秒期限吻合；自动回退时序由代码推导，不把这段日志当作现场回退数据完整性验收。

服务器连接测试、信息读取和后续恢复验证都使用 `_ensure_url` 自动补全 `http://`。新增加的密钥生效前启动检查直接拼接原地址，遗漏了该补全。Requests 对这种地址抛出 `InvalidSchema`，尚未建立 HTTP 连接；原循环吞掉异常并持续等待，期限到达后触发恢复回退。因此容器已启动仍会被错误判定为未就绪。

## 修改范围

启动检查复用现有 `_ensure_url`，保持有协议地址、原等待期限、HTTP 200 门槛、源密钥回读、API Token 同步、Commit 验证及失败回退流程。失败信息保留脱敏后的版本接口地址、最后 HTTP 状态或连接异常类型，不记录响应正文、配置文件内容或密钥。

源实例为 `172.31.8.55`，当前承接目标为 `10.10.5.21`；`10.10.5.22` 的镜像推送失败与本次地址解析失败没有已证实的因果关系。完整数据库恢复会携带镜像任务配置，不自动删除或停用用户的镜像任务。Docker 容器标准输出日志没有被此恢复代码复制；备份数据目录内原有的应用日志文件可能随目录恢复，但本次粘贴记录不足以证明日志来自主实例。

固定真实样本在独立 Docker 实例中保存无协议目标地址，走完整备份、数据库与文件恢复、密钥回读、API 和 Commit 验证、私有 Git、两步验证解密、重启及 Compose 重建。旧镜像应复现启动检查失败，新镜像应完成全部校验；已有失败回退样本必须保持通过。所测样本要求成功误报为零，原端口与挂载保持，日志不泄露密钥。
