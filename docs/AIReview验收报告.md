# AI Code Review 本机验收报告

> 历史报告：以下草稿发布及兼容补丁结论描述当时版本。当前已采用原版 Gitea 直接发布，最新工程验收见 [直接发布验收报告](AIReview直接发布验收报告.md)。本文件保留历史模型质量与测试证据，不作为当前部署补丁要求。

本报告区分工程链路、位置校验、模型质量和实际生产验收。测试在本机 macOS 的 Docker Desktop 内运行 Linux amd64 服务；未操作现有仓库策略环境。测试仓库全部由脚本生成，不含公司源码。

Gitea 草稿隔离兼容补丁已在独立实例通过 API、普通开发者页面、异步通知及发布竞争验证。原版 Gitea 1.26.4 安全降级为普通总结；精准行内需要兼容版本 1.26.4+review.1。完整业务质量目标仍未全部达到。

## 结论与适用范围

已实现 Manager 管理模块、独立 Review 数据库与 Worker、隔离 OpenCode 1.18.7 执行器及 New API HTTP 引擎。默认全局关闭，只发布 COMMENT 辅助意见。首批支持 Gitea 1.26.4（普通意见）及 1.26.4+review.1（精准行内）、UTF-8 C/C++，不承诺完整跨项目、跨线程及硬件语义识别。

**首轮模型质量未达到全部目标。** 官网 `deepseek-flash` 的 50 个固定合成 PR 中，发现 23/25 类已标注缺陷，召回率 92%；去重后的问题准确率为 23/(23+4)=85.19%，低于 95%。不能将这些结果等同于内部 New API 的 `deepseek-v4-flash`、公司真实 PR 或人工节省 80% 的验收。

工程测试和质量测试分别保存记录，失败样本不会因重试而从报告删除。部署包及最后补充测试的结果见交付验收证据；未完成的生产条件仍列为未验证。

## 人工基线、样本及指标口径

目标用户为 C/C++、嵌入式开发者与人工 Reviewer。人工流程包括阅读累计 PR diff、理解必要上下文、判断触发条件、核对因果链、定位代码、撰写意见和复核后续版本。没有收集同一组人员的实际基线工时，因此本次**没有人工节省比例的有效测量**。

固定模型样本为 `scripts/review-fixtures.py` 的 25 类缺陷及其正常对照，共 50 个真实 PR。样本覆盖数组边界、空指针、释放后读取、重复释放、泄漏、realloc 所有权、复制长度单位、字符串终止、snprintf、格式字符串、整数截断与移位、锁、线程 API、文件描述符、read 错误、ARM 对齐、MMIO、悬空引用、迭代器及数组释放。

基准以新建文件的小 PR 为主，不能代表大型历史仓库的上下文复杂度。基础设施故障修复后才得到成功链路的样本仍保留原始失败记录；模型误报、漏报不通过重试替换首轮结果。完整首轮数据见 `AIReview验收证据/五十样本首轮结果.json`。

| 指标 | 目标 | 实测与结论 |
|---|---|---|
| 缺陷召回率 | ≥80% | 23/25=92%，仅此合成模型集达到 |
| 问题准确率 | ≥95% | 去除同一缺陷重复项后 23/27=85.19%，未达到 |
| 原始意见中独立且有价值的问题比例 | 不作为替代准确率 | 23/28=82.14%；另有 4 条误报、1 条重复 |
| 固定位置算法样本 | 错误行内为 0 | 50 组确定性位置子样本及真实边界用例通过；不代表模型语义位置永不出错 |
| 可定位有效问题的行内覆盖率 | ≥90% | 首轮 23 个独立有效问题有 22 个可靠行内位置，1 个重复释放位置因原文重复降级，95.65% |
| Webhook P95 | <1 秒 | 100 次真实 HMAC 请求 P95 10.99 ms |

| 人工节省 | ≥80% | 未测量，不宣称达标 |

位置的“真实改动行存在”和“模型选到了缺陷原因”分别审查。正常样本上的误报即使锚点合法也不算正确意见。

## 首轮模型错误及反证复核

| 样本 | 观察结果 | 复核结论 |
|---|---|---|
| case-14 | 对接管所有权的 realloc 正常实现提出两条调用方悬空指针意见 | 头部明确说明调用方不再释放旧指针；模型违背已提供契约，两条均为误报 |
| case-28 | 要求 clear_prefix 清零最后一项 | 未提供必须清零整个数组的约束；已有 n>0 防护，属于误报 |
| case-44 | 要求合法 volatile MMIO 忙等待增加超时 | 没有必须超时的硬件/业务契约；属于缺少依据的推断 |
| case-31 | 未报告 C 语言负数左移 | 漏报；当前运行基准不是 C++20 的对应规则 |
| case-43 | 未报告普通指针轮询异步 MMIO | 漏报；缺少 volatile 可能导致优化后不再读取硬件寄存器 |
| case-41 | 同一未对齐读取分别评论契约注释与实际读取行 | 有一条重复且位置不适当；已禁止纯注释独立作为可执行缺陷锚点。干净部署复测为 1 条有效意见、实际读取第 14 行，无注释行评论 |
| case-05/15/19 | 原始预期行集合比合理的因果位置更窄 | 分别讨论 malloc 返回值、错误容量检查、snprintf 调用，均在正确函数且属于原因位置；保留原始“位置失败”记录及这项人工裁定，不作为模型错误归零的隐式重标 |

不通过增加提示词或隐藏正常对照失败来宣称质量达标。生产试点需要在实际内网模型下补充已标注公司 PR，明确硬件/所有权契约，并重新测量精确率、召回率、定位和人工复核成本。

## 工程与异常测试

已执行原有后端测试及新增定位、签名、租约、结构化输出和发布状态机测试，116 项通过；定位测试还含 50 组子样本。前端生产构建通过。原有策略中心等未提交改动保留，没有重新初始化或覆盖其测试数据。

真实 Gitea 边界测试覆盖新增、修改、删除行、删除文件、重命名、中文及空格路径、多修改区域、CRLF、末尾无换行、相似函数、重复原文、错误锚点、错误引用及不可映射位置。预期降级均生成普通意见，无猜测性行号。

真实 Git 流程覆盖多 Commit 累计 diff、后续 Push 移动行号、rebase、force-push、人工新代次和 Worker 强制中断后的租约恢复。旧模型结果被失效状态阻止；历史问题引用原讨论，新版本锚点重新计算。覆盖不足明确显示，不能给出完整无问题结论。

真实 Gitea 发布竞争驱动分别在取 diff、PENDING 创建、COMMENT 创建之后插入新提交，并模拟成功响应丢失和租约过期。五项通过：过期草稿仅清理自身；最终瞬间竞争仍保存原 SHA 并标记历史；成功响应丢失后回读原 Review，不重复提交；原有开发者讨论保留。证据见 `真实发布竞争-1789143545.json`。

模型 429、500、非法 JSON、工具调用、错误引用及中断使用协议替身故障注入。正常成功链路另外使用真实模型，不能用替身结果计入模型质量指标。

只读与网络实测确认执行器非 root、根文件系统不可写，无法读取 Manager/Review 数据库、SSH 密钥或 Docker socket；公网 TCP 和外部 DNS 被阻止，内部受限网关仍可解析访问。生产 Worker 的外联白名单仍需部署网络策略配合，不能只靠提示词限制。

## 测试发现并修复的根因

1. OpenCode 每次执行会提取动态库到共享临时目录，连续运行后累积 74 个文件、约 402 MB，耗尽 384 MiB tmpfs，导致 CLI 无法启动。已将 TMPDIR/TMP/TEMP 统一放进每次调用目录并销毁；修复后的 40 次连续真实 CLI 审查通过，末尾记录的临时目录空间为 0。不是凭据故障，不依赖盲目重试。
2. 原版 Gitea 创建 PENDING 后再 CreateReview COMMENT 会留下两条 Review 时间线记录，且先公开草稿。最终实现通过兼容补丁使草稿完全不创建动态；原版只生成普通正式总结。旧草稿恢复仍仅依据机器人身份、任务标记和服务端 Review 链接处理自身记录，不清理开发者讨论。
3. Gitea Review 列表先分页再过滤不可见草稿，普通评论列表则完全不分页。适配器分别按真实接口处理，避免长 PR 下误认为标记不存在或重复收集普通评论。
4. 历史意见在多次人工重审后需要保持最初 Review 引用，已修复超过十次重审后的传递去重；人工完成后确认当前执行代次的真实版本，避免无意义补排同版本任务。
5. Gitea 评论展示片段会截断并保留完整 hunk 计数，还会归一化 CRLF；校验器仅接受已验证的展示差异，完整补丁仍逐字节重建。
6. 模型 finish_reason 为 length 时，OpenCode 可能仍输出合法 JSON。统一转发端现验证完整结束状态、SSE 结束标记和工具调用，拒绝截断结果，不能因为 JSON 合法就表示审查完成。
7. nginx 原先固定解析 backend 容器地址，容器重建后可能继续访问旧 IP；现使用 Docker DNS 动态解析，重建后真实管理接口恢复正常。
8. 基础 Compose 原有固定会话密钥和默认密码不适合保存新增模型凭据。AI Review 部署覆盖文件现在强制要求显式配置 SECRET_KEY 与 INIT_PASSWORD，避免该部署路径继续使用公开默认值。
9. 浏览器发现 Gitea 将总体状态中的相对 Review 链接按仓库文件路径改写。进一步实测发现 API 的完整地址会带 Worker 内部容器名，外部开发者仍无法点击。最终改为当前 PR 内经路径和格式校验的 issuecomment 片段链接，同时避免文件路径改写与内外地址不一致；修复后的普通开发者页面已实际点击确认跳到同一 PR 的 Review 动态，最终包重新部署记录单独保存。
10. 草稿可见性实测发现原版 1.26.4 的公开时间线及通知暴露 PENDING 意见，文件页/API 隐藏不能提供完整隔离。已增加原版安全降级，并单独准备 `1.26.4+review.1` 最小兼容补丁，使 PENDING 不产生公开动态与通知；该条件下五种真实发布竞争通过；普通开发者页面证实发布前隐藏、发布后新侧第 2 行可见，同一 Review ID 仅产生一条正式动态。首次通知检查早于异步队列完成，后续回读确认正式通知，未重发 Review。证据见 `兼容版本私有草稿验收.json` 和 `兼容版本真实发布竞争.json`。
