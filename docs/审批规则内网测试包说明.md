## 核心测试方式

在有 Docker Compose、Python 3.9 或更高版本和 Git 的 Linux x86_64 测试机准备一个新目录。离线包包括运行镜像，无需下载 npm/pip 依赖。压缩包、同名 `.sha256` 文件一起保留，先核对摘要再解压：

```bash
sha256sum -c gitea-manager.tar.gz.sha256
mkdir approval-test
tar xzf gitea-manager.tar.gz -C approval-test
cd approval-test
docker load -i offline/运行镜像.tar
python3 scripts/approval-integration.py --image-tag offline --packaged --ui-window-seconds 7200
```

这个入口只创建新容器、新持久卷和随机端口，不接受生产地址。先执行固定功能样本，再保留最多两小时人工页面窗口，结束后回退组件并停止本次容器，保留卷和证据。不要把它用于已有生产实例。镜像实际运行在 Linux amd64；开发机上的 Docker Desktop 仿真不等于目标 Linux 主机验收。

页面地址在终端显示；账号和随机口令保存在本次 `work/审批可行性-运行标识/页面验收入口.json`，权限 0600，不可公开。Manager 使用该口令；Gitea 可分别用 `author`、`alice`、`bob`、`carol`、`dave` 和 `probe-admin` 登录，模拟作者、审批人和管理员。组成员及稳定 ID 可在 Gitea 组织页面核对。

入口只绑定测试机 `127.0.0.1`。远程浏览时，通过 SSH 分别转发终端显示的 Manager/Gitea 端口，再在本机访问。退出浏览器不会停环境；写入本次目录的 `页面验收结束` 文件可提前结束窗口并执行回退。命令仍在运行时保留终端连接。剩余未合并的样本及新建 PR 可用于手动批准、撤回和更新代码；切换安装期间不要同时创建 PR，相关切换缺陷仍待修复。

重点观察：三人总票、两组各一票、跨组总数去重、缺组说明、原生要求并行显示；新增要求满足不等于所有原生检查均通过。页面失败或过期不能显示当前通过。正式强制启用按钮不可绕过；上述隔离脚本通过本次唯一实例标签绑定强制测试资格。

独立的真实会话与代理功能回归可以另行运行：

```bash
python3 scripts/approval-view-matrix.py --image-tag offline --packaged
```

它创建自己的样本，顺序验证不同身份、撤权、账户停用、退出登录、代码变化、关闭 PR、展示停机与组件移除，不是多用户同时发压。

## 接入已有测试 Gitea

已有测试 Manager 可使用包内 `upgrade.sh`，升级流程仅管理 Manager 服务；把压缩包、校验文件、`upgrade.sh` 放在同一目录，先执行 `bash upgrade.sh --container 测试Manager后端容器名 --check`，核对目标后执行不带 `--check` 的同一命令。不要选生产 Manager。本轮离线升级对新增展示服务、原数据卷及中断回退另外复验。

已有 Gitea 只允许从 Manager 导出默认影子组件，再按《审批规则使用与接入说明》预检、安装及配置同源代理。支持官方 Gitea 1.26.4、PostgreSQL、组织仓库和明确分支名。只读访问 PostgreSQL 标记用于弥补原生时间线 API 不完整；不修改 Gitea 表结构或历史。其他数据库类型、不可确认的数据库连接及不兼容权限配置会拒绝预检，不擅自修改现有审批池或保护规则。

普通 `deploy.sh` 会构建镜像，不是本包离线复验入口；不要用它替代上述固定镜像流程。代理热重载依赖现场已有能力，安装器不会覆盖代理配置或重建 Gitea。页面卸载与门禁停用分别操作，详见使用说明。
