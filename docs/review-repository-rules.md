# 仓库级自定义审查规则

## 使用

在被审查仓库根目录创建 `.gitea/review-rules.md`，使用普通 UTF-8 Markdown 编写项目背景、审查要求、适用范围和例外。内容由仓库维护者维护，沿用现有 Git 提交与审批流程。文件大小上限为 32 KiB。

示例仅展示写法，使用时请替换为项目自己的要求。

```markdown
# 项目审查要求

## 项目背景

说明运行环境和业务约束。

## 重点检查

写明希望审查员检查的条件，以及判断依据。

## 例外

说明哪些情况符合项目约定，并提供必要背景。
```

合并该文件后，后续 Codex 审查自动读取任务固定目标提交中的规则。PR 同时修改规则时，本次仍使用目标分支的版本。目标分支可以是任意受支持的 PR 目标分支。

## 查看生效内容

打开审查任务详情，在执行配置所在页签找到“本次自定义规则”。这里显示规则状态、目标提交和原文 SHA-256。“查看冻结规则”展示该任务保存的正文，并提供固定提交文件链接。

“已加载并提交模型”表示该任务加载了规则并已发起模型调用。模型对任意自然语言要求的理解效果需要结合实际意见检查。文件缺失显示“未配置”，空白文件显示“内容为空”，二者使用默认审查。

规则加载失败时任务停止并保留诊断。请修复编码、大小或文件类型后重新审查。符号链接、目录、子模块和 LFS 指针均不作为规则正文。

## 版本与执行

Manager 直接读取 `base SHA` 的 Git 对象，保存原文、摘要和协议版本。主审、每项独立反证及历史问题复核使用同一份内容。恢复任务使用已冻结的内容，目标分支变化仍受任务版本校验保护。

规则内容作为项目审查指令提供给 Codex。只读能力、结果格式和 P0/P1 证据门槛由系统控制。规则涉及的意见应引用规则标题或原文，并提供代码证据。历史规则删除或放宽本身不能证明代码已经修复。

当前入口为单个 `.gitea/review-rules.md`。其他指令文件与 Markdown 链接不会被自动作为补充规则加载。审查需要读取相关源码时仍使用固定版本源码工具。

新 Codex 任务使用规则协议 1。升级前任务保留协议 0，新数据库字段默认为 0。OpenCode 执行器已标记弃用，本功能适用于 Codex。

## API

现有任务详情增加 `review_rules` 元数据，不携带正文。`GET /api/ai-review/tasks/<job>/rules` 返回冻结内容、状态、来源提交、SHA-256 和文件链接。访问权限与任务详情一致，包含登录、组织及仓库权限检查。

规则随任务数据保存，使用既有备份与访问控制。普通任务列表不返回正文。

## 验证入口

后端定向测试包含 `backend/tests/test_repository_rules.py`。界面验证入口为 `node scripts/test_review_rules_ui.cjs`，使用生产构建和无头浏览器。

运行 `python3 scripts/review-rules-acceptance.py` 生成二十组正反例，共四十个固定样本，并验证预置代码的行为。输出位于 `work/review-rules-acceptance/`。

在已初始化的独立本机验收环境中，设置 `REVIEW_STATE_DIR` 后追加 `--run`。脚本创建独立命名的测试仓库，在无规则和有规则两组各创建四十个 PR，保存实际任务及模型结果。实际运行要求环境已配置 Codex 与部署使用的 DeepSeek 模型。`--limit` 仅用于探索，小样本不能作为完整验收。

人工基线应覆盖阅读规则、检查代码和复核结果的时间。结果文件保留人工核验、人工基线秒数和人工复核秒数，待独立复核人员填写。准确率、召回率和人工节省结论以复核结果为准。

独立核验时，为每条结果的 `人工核验` 填写 `正确意见数`、`错误意见数`、`漏报数`、`P0P1误报数`。填写人工基线和复核秒数后运行同一脚本的 `--score`，计算双组准确率、召回率、Token、耗时和人工节省。缺少完整八十条结果、人工核验或耗时时，脚本拒绝生成质量通过结论。

验收运行目录已有 `runs.json` 时必须选择新的 `--output`，以保留首次记录。运行期间若模型配置版本变化，脚本停止该次对照并保留现场。
