# AI Review 重装后的 Webhook 密钥绑定修复

日期：2026-10-27。

## 触发条件与原因

卸载并重新安装 Manager 后，新的 Review 数据库生成新密钥，Gitea 中相同回调地址的旧勾子仍然存在。原接入流程向该勾子发送包含 `config.secret` 的 PATCH，并据回调地址、事件和启用状态判断安装成功。

官方 Gitea 1.26.4 和本次验证的增强版均不会通过该 PATCH 更新密钥，也不在读取接口返回密钥。因此接口成功并不代表两端密钥一致。这与此前原始请求体被提前读取的问题是两个不同原因。

## 修复行为

- 为尚未建立可信绑定的仓库创建携带当前密钥的新勾子；保存随机名称、目标摘要和创建阶段，回读成功后只清理本次记录的相同回调旧勾子。
- 已确认的绑定在重复检查时复用；不会每次检查都更换勾子。
- 创建响应丢失时通过已持久化的随机名称核对原回执，不盲目再次创建。删除响应丢失时先查询旧编号；明确拒绝创建则允许修正权限后重试。
- 新勾子回读失败、旧勾子被他人修改、同一回调存在未知重复勾子时保留现场并返回错误。跨进程仓库锁串行化安装操作。
- 内部绑定信息不返回浏览器，也不接受客户端覆盖。原始请求体缓存、严格 HMAC 验签和临时 Push 订阅恢复继续生效。

## 验证

- 最终 Linux amd64 后端镜像中 172 项相关回归通过，包括 10 项绑定生命周期用例、原始请求体验签、自动接入、默认预算、思考标签、证据编号与审查解析。
- 使用独立官方 Gitea 1.26.4 和增强版 `enhanced-20261026-r14`，均复现 PATCH 后数据库仍保留旧密钥以及真实投递 403。
- 两种版本均验证：创建新勾子后数据库密钥一致、旧勾子删除、重复检查不再创建、真实签名投递成功、临时 Push 订阅恢复、再次模拟全新 Manager 状态后仍可恢复。
- 伪造签名仍返回 403。所有验证仅操作本次创建的隔离实例，结束后清理其容器、卷和网络。

## 审查结论与边界

VERDICT: PASS

P0/P1 BLOCKERS: 无。已检查创建与删除的响应丢失、重复调用、跨进程互斥、目标身份、密钥轮换、内部状态输入与输出、回调验签，以及其他用途勾子的保护。

UNVERIFIED RISKS: 用户实际宿主机上的安装、网络与最终接入结果仍需现场确认；实际内网模型质量和人工精力减少 80% 未验证。创建结果未知且始终查不到回执时保持停止，需核对 Gitea 现场后恢复；不以无限重试换取表面成功。

NON-BLOCKING FINDINGS: 既有 SQLAlchemy 旧接口告警与前端大分块告警。

人工基线是识别实际容器、比较密钥、删除旧勾子和重新接入；本修复自动处理正常的重装与重试路径，保留真实异常供人工处理。无需重新安装 Gitea 或关闭签名验证。部署新版 Manager 后，在现有仓库执行事件通知的安装检查或继续自动接入即可。
