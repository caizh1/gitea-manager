# 最终形态预迁移、整批开放与恢复

## 目标与范围

平台管理员完成来源盘点和人员确认后，由系统完成重复的完整性与可执行性核对。人工基线为逐仓库迁移、逐类核对附件及规则、逐次处理失败；目标是减少至少百分之八十的重复操作。固定样本的正确性、耗时和操作次数分别记录，真实企业规模未经测量不宣称达标。

目标接收协议升级为第五版，要求整批开放和容量探测能力；旧接收端、旧的预迁移通过结果不能直接用于新流程。旧任务保留历史状态，不重写检查点。

## 每次迁移流程

1. 检查 Manager 和目标盘的字节容量、inode、存储可写与数据库写入能力；预算包含多份工作副本及四 GiB 安全余量。
2. 在管理员隔离区完整导入代码、LFS、Wiki、协作历史、附件、制品、规则与 CI 历史。
3. 将仓库准备到最终群组，实际安装并回读保护规则，按原生协议回读制品。此时第五版接收端仍禁止普通业务账号、Actions 身份和仓库搜索访问该批次内容。
4. 核对全部仓库后生成整批发布凭证。固定最终归属、规则、仓库单元及群组链修订，全部准备完成才允许进入正式启动前复检。
5. 用户确认来源停写，系统再核对源内容、人员、权限、目标对象与容量。
6. 正式开放只更新同一批次的可见性和最终归档状态，不再次搬运数据或首次安装规则。数据库事务使整批开放一起成功或一起回滚。

## 中断与取消

- 工作盘与目标盘每五秒持续探测，空间或 inode 不足会停止写入并保留检查点。容量恢复后可继续同一预迁移。
- 附件服务端写入成功但回执丢失时，按原会话与来源标识核对，不创建替代附件。
- 执行器重启将运行中记录转为中断；继续时复用同一批次、仓库和回执。
- 开放回执丢失时，先读取接收端已提交状态，再恢复 Manager 状态，不能再次创建或迁入。
- 取消尚未开放的预迁移时，只回收该批次可以证明归属的原生制品发布记录和路径；原始文件保留在归档隔离副本。发现外来内容则拒绝回收，不覆盖或删除人工新增资料。
- 已开放批次不允许通过预迁移取消接口撤销业务数据。

## 验收要求

开发验收使用隔离 GitLab CE 与 Gitea 实例，覆盖全部固定合并变体、跨仓库请求、六类制品、历史 LFS、CI 子流水线和触发作业；单独执行回执丢失、进程崩溃、实际小容量存储与整批可见性测试。用户每次迁移只运行本次资料的预检查和最终形态演练，不人为注入断网或崩溃。

支持边界仍不包含 OCI；GitLab EE 付费能力继续标记未验证。运行于本机虚拟化环境的通过结果不能替代真实生产宿主机、任意版本、永久存储损坏或大型企业容量的证明。
