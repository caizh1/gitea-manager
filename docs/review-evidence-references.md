# 分批证据引用与真实模型验收

## 历史编号协议的修复边界

已观察到的失败是：模型接收了正确的本批证据，但报告使用了本批不存在的全局证据编号。编号出现在其他批次，不能单凭这一点证明会话串批。

当前新任务使用 [源码位置协议](review-structured-protocol.md)；本节记录第二版编号协议及其历史兼容行为。第二版证据协议中，模型仅看到当前单元的短编号；每个编号同时标识证据和可用的评论位置。源码行号作为独立字段提供，不能用来拼造编号。文件原名、新名在文件表保留，不在每一行重复。原始证据、全局编号和评论位置仍保存在计划中，由程序精确映射，模型不能借用其他批次的证据。

历史计划没有新协议标记，继续使用原有契约；不会静默重编号或重写已有结果。原来合法的全局编号、明确的定位别名以及完整思考前缀、外围 JSON 围栏兼容仍由历史解析器处理。

## 严格校验与一次纠正

- 引用必须属于当前单元；定位必须指向引用列表中的可评论证据。缺字段、非法类型、无效 JSON、输出截断仍然失败。
- 仅在已确认完整返回、回执完成且出现引用越界或定位失配时，允许一次新的独立会话只纠正原报告的引用字段。意见内容、数量、顺序、级别和其余字段必须不变；即使返回合法空报告也会被拒绝。首次原始响应与失败诊断保留，不把错误意见静默删除。
- 第二次仍失败则停止该单元。网络、鉴权、未知结果、回执丢失、截断或 JSON 错误不触发此纠正；未知结果仍须核对原会话。
- 每个主审／关联单元最多主审与反证各一次正常调用、各一次引用纠正。新计划调用上限包含这些额度，仍受成本确认和总时间预算约束。上下文拆分也重新计算上限，不借用未授权额度。
- 自动失败检查本身仍只读；它不执行重试。纠正由持久化的分批执行状态机执行。

## 验收基线与方法

目标用户为审查嵌入式固件变更的开发者。人工基线是逐段检查一千行合成固件、定位十二处严重问题并在 PR 中回写；人工实际耗时尚未测量，不能宣称已减少八成工作。

`scripts/review-evidence-acceptance.py` 生成一千行 C 代码，每八十行一个预埋问题，共十二个。场景覆盖报文边界、DMA 所有权、固件签名、启动银行、温度保护、鉴权、中断、地址溢出、看门狗、描述符环、欠压写入和 DMA 长度。每个问题都由固定输入触发；有缺陷版本十二个断言均失败，修正版本十二个均通过。答案、测试探针和修正版仅保留在本机工作目录，不提交到被审查 PR，也不放入模型提示。

验收必须区分两项：

1. 工程闭环：真实 Git 提交、Gitea Webhook、Manager 分批、原生执行器、官方模型、严格解析及 Gitea 正式回写均完成；每项位置属于冻结提交和本单元证据。
2. 审查质量：人工逐项比对十二个问题，统计检出、漏报、有效额外问题、误报和重复意见。成功状态、文本覆盖率及合成样本结果都不等于真实生产质量保证。

运行前须创建独立 Compose 项目与持久卷、挂载当前源码、配置工作区共享卷和执行器目录权限。脚本读取外部密钥文件，运行时经管理接口加密保存；密钥文件、数据库和原始模型响应不提交。测试允许成本确认；除当前测试任务外，不自动批准其他任务。

## QEMU 原始场景复现

用户补充的场景基于 QEMU `v11.0.1`，上游提交为 `6e9a825c1d4e7b62d072e99a89ecd1a74c7f0d55`。测试基线的源码树与该版本一致，不导入原始提交历史。网页复制内容缺少逐行增删符号，因此先根据同版本旧内容重建差异；十四个旧文件变更块的新旧行号及行数均匹配，新增 `ufs_ext.c` 的九百一十四行逐行一致。换行统一为 LF。

采用 Git 的 histogram 算法后，变更统计与原粘贴内容吻合：`meson.build` 新增一行、删除一行；`ufs.c` 新增五十七行、删除三十一行；`ufs.h` 新增五十一行；`ufs_ext.c` 新增九百一十四行。Manager 实际计划覆盖一千零五十五个增删行，八个主审单元、二十八个关联单元。

真实高思考运行的两个单元出现本批编号错误，其中一例把编号多写一位。首次结果均被严格拒绝，第二次在独立会话中完成引用纠正；两个单元分别三条、四条意见的数量、顺序、级别和正文均保持不变。原始响应与校验记录保留在隔离测试实例中。这证明运行机制能够处理实际模型产生的编号错误，不代表模型以后永不出错。

高思考任务在另一单元耗尽三万二千七百六十八个输出 Token，未生成报告正文，以 `length` 结束。这是独立的模型预算限制，未放宽校验来绕过。随后使用现有的 `reasoning_effort` 协议、启用思考并选择 `low`，在相同输入与输出额度下重审同一 PR；此前耗尽输出的单元已完整通过。该次低强度任务最终在第 35 次调用因 JSON 语法错误停止，作为失败基线保留。控制参数依据 [DeepSeek 官方思考模式文档](https://api-docs.deepseek.com/guides/thinking_mode/)，不能据此声称所有内网兼容服务均接受该参数。

## 已完成的合成样本结果

千行合成样本的七十二次真实模型调用全部完成，没有引用失败；八个主审、二十八个关联复核和三十六个反证单元均完成。逐次核对 Broker 保存的实际用户消息与单元、原生会话绑定，全部匹配；所有被接受的结果再次通过严格校验。主审变更行覆盖一千行且不重复。

十二个预埋严重问题均检出并在独立反证中保留。最终保存一百二十一条行内意见，独立回读确认全部位置、数量和提交版本匹配。意见重复明显，不能称为一百二十一个独立缺陷，也不能据此宣称已达到八成人工节省或普遍的精确率目标。

大样本还暴露了原有发布回读问题：Gitea 1.26.4 的 Review 评论接口直接返回完整数组，不使用分页参数，也不提供总数头。原分页循环重复读取一百二十一条评论直至达到上限。现已对该明确接口采用单次完整读取，并检查条目编号、唯一性和可选总数；普通列表仍逐页读取。修复后只核对已发布回执，正式 Review 数量仍为一，模型调用仍为七十二，没有重复创建评论。

测试实例挂载当前源码并使用已有依赖镜像，属于工程链路验证，不是新安装包或真实硬件验收。两项任务都使用六万五千五百三十六输入、三万二千七百六十八输出，单次请求六百秒；为完整测试设置三小时总执行预算。

当前源码位置协议的完整执行验证见 [流程优化验收](review-flow-optimization.md)。按用户最新要求，本轮只确认结构、位置、完成状态与发布链路，不重新核对缺陷内容。未生成安装包或发布镜像。
