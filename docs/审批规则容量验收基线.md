# 审批规则容量验收基线（千人研发规模）

状态：按用户最新要求，全部多用户容量与双 24 小时测试在内网功能测试包交付后继续。已有短时校准包含失败，500/1,000 用户尚未通过，不能宣称千人生产容量。已完成的有限集成、页面和合并耗时证据仍见《审批规则开发验收报告》。

## 人数与流量的区分

2026-09-13 用户提供：“我们研发大概按1000人规模算，峰值估计能有1/2就不错了吧”。据此采用研发总人数 1,000、估算峰值同时活跃 500；两倍峰值为 1,000。常态 100 人只是测试暂定值。这里的“活跃”不能解释为每秒请求数，也不能视为实际同时打开 PR 的人数已测得。

为了单独验证展示组件的上限压力，再安排每名活跃用户一个可见 PR 页面：当前组件在上次请求结束后等待 15 秒再刷新，隐藏页面停止轮询。忽略响应时间的理论持续请求上限为可见页面数除以 15；响应越慢，实际闭环请求率越低。因此必须同时记录计划负载、实际发出数、完成数、超时和调度延误，不能把服务变慢导致少发请求当作容量通过。

| 档位 | 活跃人数假设 | 专项可见 PR 页面数 | 15 秒间隔理论请求上限 | 状态 |
|---|---:|---:|---:|---|
| 常态 | 100 | 100 | 约 6.67 次/秒 | 未执行；常态人数为暂定 |
| 估算峰值 | 500 | 500 | 约 33.33 次/秒 | 未执行；人数来源于用户估计 |
| 两倍估算峰值 | 1,000 | 1,000 | 约 66.67 次/秒 | 未执行；压力档 |

500 或 1,000 人集中打开页面的首轮请求应另测突发，不能用均匀分摊后的请求率代替。多窗口、多标签需分别覆盖可见和隐藏状态；一个后台隐藏标签不能当作一个持续轮询用户。

## 混合业务的暂定输入

人数不足以推导写操作频率。下表仅作为隔离负载生成的初始参数，后续用现场脱敏统计替换；不是生产实测，也不是已通过的吞吐指标。参数以 `审批规则容量负载配置.json` 保存。

| 操作 | 每名活跃用户的暂定间隔 | 500 人每分钟计划量 | 1,000 人每分钟计划量 |
|---|---:|---:|---:|
| 普通页面导航 | 120 秒 | 250 | 500 |
| SSH/HTTP 拉取 | 300 秒 | 100 | 200 |
| SSH/HTTP 推送 | 600 秒 | 50 | 100 |
| 原生批准或撤回 | 1,200 秒 | 25 | 50 |
| 创建 PR | 3,600 秒 | 约 8.33 | 约 16.67 |
| 合并 PR | 3,600 秒 | 约 8.33 | 约 16.67 |

审批展示轮询与上述原生流量同时执行。SSH 和 HTTP 各占 Git 操作的一半。批准、撤回、请求修改、评论须使用不同确定性序列；合法合并与故意缺票合并分别统计，预期拒绝不能算服务失败，也不能掩盖错误放行。每次合并核对真实目标引用，不以 HTTP 状态独立判断。

所有身份、仓库和秘密仅创建在新建、独立标记的隔离实例。500 用户档必须使用 500 个独立登录身份；不能用一份管理员 Cookie 代替权限隔离验证。造数失败或人数不足就停止该档，不降低人数后沿用原档位名称。

## 需要独立执行的子用例

以下每行均为未执行，不因配置文件存在或小样本通过而改变。

| 编号 | 场景 | 核验重点 |
|---|---|---|
| 容量01-A | 未接入，按三档分别运行相同原生业务序列 | 三份独立基线；失败或宿主机资源不稳定则不能做回归百分比结论 |
| 容量01-B | 影子模式，三档分别安装、正常运行和回退 | 原业务零新增失败，P95 回归不超过 5%，会话/连接/启动时间保持 |
| 容量01-C | 隔离强制模式，三档运行相同序列 | 新 PR 正确拒绝/放行；存量和其他仓库保持原流程 |
| 容量02-A | 100、500、1,000 个可见 PR 页面分别持续轮询 | 达到计划页面数；记录端到端及 Gitea 下游请求放大、在途数和排队 |
| 容量02-B | 500 个页面集中打开 | 首轮突发；不能拖慢原生页面和合并门禁 |
| 容量02-C | 1,000 个页面集中打开 | 两倍突发；超出容量时状态失效可见，不能显示错误通过 |
| 容量02-D | 500 人反复开关标签、隐藏恢复、双窗口与账户切换 | 无遗留轮询、连接和跨账户结果；分别统计可见页面数 |
| 容量03-A | 同一热点 PR 占展示请求 50% | 热点保护不能缓存合并授权或跨身份复用权限结果 |
| 容量03-B | 请求均匀分散到多个仓库和 PR | 不能以热点结果命中率代替分散负载能力；稳定仓库/PR 身份隔离 |
| 容量03-C | 审批池 1,000 人，单组 500 和 1,000 人，多个重叠组 | 分页完整、资格正确、请求预算不足明确失败；不增加无限读取预算冒充扩容 |
| 容量03-D | 同一 PR 有 1,000 条审批/评论/提交事件 | 最新有效批准及代码绑定正确；长历史与用户数单独记录 |
| 容量04-A | 500 页面读取时执行规则编辑、预检及合并 | 显示请求不能占满管理和 Hook 服务；原生规则仍独立生效 |
| 容量04-B | 两倍页面负载时并行备份、统计、策略和 AI Review | 队列、CPU、内存、磁盘和下游 API 有界，原有任务无新增失败 |
| 容量04-C | 500 页面读取期间停止审批服务并恢复 | 过期状态清除、无重试风暴；新受管 PR 故障阻断，存量仍无远程依赖 |
| 容量05-A | 影子模式连续 24 小时 | 常态、估算峰值、两倍估算峰值各 8 小时；全程保留业务及资源序列 |
| 容量05-B | 隔离强制模式连续 24 小时 | 同上；门禁 P95 ≤3 秒、硬超时 ≤10 秒，全部实际引用判定正确 |
| 容量05-C | 长测后重启扩展服务、查看积压并卸载 | 审计/日志有保留上限；无积压放大；合法业务数据完整 |

实际运行顺序从小规模校准开始，再到 100、500、1,000。出现错误引用写入、原生业务新增失败、超时失控或隔离资源上限被触发时，停止升档，保留首次失败、实际达到的负载与日志。修复后重跑失败档及受影响回归；不能只延长超时、降低发压频率或隐藏失败请求取得通过。

## 当前实现需要验证或补齐的能力

- PR 展示已拆为独立服务（两个进程、每进程八个线程），与管理及 Hook 分开；使用 Manager 数据库中的短时状态缓存，每次仍校验原生浏览者权限。此拆分和单页通过不等于 500 页面容量通过。
- 一次状态查询既要确认原生页面权限，又要读取原生审批、团队和分支信息。必须测量真实下游请求放大；不能只测展示接口返回缓存的速度，更不能让页面缓存成为合并放行依据。
- 跨页面的读取协调、审计保留、队列和日志上限、大团队读取成本仍属于待开发/待验证范围。任何优化都必须保留账户切换、撤权、审批撤回、代码变化和失败清除状态的测试。
- 当前本机运行多个其他独立开发环境，且缺少生产宿主机规格、仓库分布及脱敏真实负载统计。本机隔离结果只能证明该次资源配额下的表现，不能直接换算现场千人容量。

估算负载通过后可以表述“在所列配置下通过 500 活跃用户假设负载”，不能表述为“已通过真实生产峰值”。24 小时长测、目标现场验收、人工精力减少 80% 和 APR-RACE-001 的发布门禁继续独立保留。
