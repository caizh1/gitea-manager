# 重启负载边界记录

隔离 QEMU TCG 环境配置为 4 个虚拟 CPU、6 GiB 内存。初次重启时，实验遗留的三套 Manager 和三个 Gitea 同时启动。核心服务恢复，正式执行器的版本检查超过 30 秒，主线程处于运行状态、其他线程包含 futex 等待；页面明确报告 AI 不可用，没有继续发布就绪。

这是实际启动超时证据；CPU 争用是合理推断，不能仅凭这些状态确定为唯一根因，更不能认定缺少 AVX。保留原始证据于验收工作目录，停止额外实验实例后另行进行单套最终包重启验收，不覆盖首次失败。

首次等待脚本还存在 SSH 启动期 TimeoutExpired 未捕获的问题，已修复；这属于测试工具缺陷，不能用来判定产品未恢复。

单套复验仍出现失败：版本检查 20.59 秒通过，服务已监听，服务/会话阶段约 32.17 秒后返回会话 ReadTimeout=2 秒。因此“仅因多套 Manager 争用”不能作为确定根因。

代码确认会话 POST 超时后会重复创建，固定 2 秒阈值也没有充分使用服务总预算。已修正为健康通过后，在剩余 30 秒总预算内只创建一次会话，并记录两段 HTTP 耗时。两个针对慢响应和禁止重试的回归测试通过；该修复不代表已经证明唯一根因，仍以新镜像实测结果为准。
