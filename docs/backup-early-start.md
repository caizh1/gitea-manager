# 固定导出后恢复源站

## 行为

源站只在一致性导出期间停写。数据库、仓库、Actions 制品、启动秘密、SSH 身份和校验元数据固定到独立本地 Docker 卷，导出助手退出后恢复原先运行的 Gitea，通过健康检查并释放本次源端锁，再由无网络、无业务卷、只读挂载的接收助手传输副本。原先停止的源站保持原状态。

接收时逐文件核对大小和 SHA-256，组装原有 ZIP 格式，再保存 Commit 校验记录及最终摘要。成功记录持久化之后才清理源端副本。失败副本保留到重新接收成功或管理员明确丢弃。重新接收从文件开头开始。

## 管理入口

备份页面显示源端副本状态、大小、源站恢复时间和停机耗时，详情显示传输总量、速度及预计剩余时间。失败记录提供重新接收和清理源端副本，成功但清理失败的记录提供清理重试。

平台管理员接口沿用登录、CSRF 和实例互斥。

- `POST /api/backups/<id>/retry-transfer` 创建独立接收记录，共享原固定副本。
- `DELETE /api/backups/<id>/source-export` 清理共享副本。没有成功接收记录时，需要 JSON 参数 `confirm_discard=true`。

同一导出的接收与清理共享进程锁。运行中或尚未收尾的任务阻止清理。删除备份记录前须处理它保留的源端副本。

## 支持边界

沿用现有 Docker 本地或 SSH、专用 PostgreSQL 与持久目录准入。停机仍包含源端导出和摘要计算。源站停写期间 Manager 完全失联时，恢复依赖管理连接重新可用。

旧备份继续使用原恢复格式。旧运行中事务沿用原归属验证。已经人工启动源站的旧任务需要单独核实收尾。新增代码不能使其成为有效备份。

## 验收口径

使用隔离 Gitea 1.26.4 与 PostgreSQL 实例，验证源站先恢复、传输期间业务写入、原备份点恢复、失败保留及重收、精确资源清理。本机 Docker Desktop 的 Linux amd64 仿真证据不能替代内网宿主机验收。真实内网停机时间、总耗时及人工精力减少 80% 尚待实测。

## 本次验证记录

- 备份相关回归 58 项通过，包括真实文件锁、进程中断恢复、摘要错误、旧记录兼容、空间不足、并发重收与清理保护。
- 本地 Docker 和远程 SSH 真实导出、提前恢复源站、独立目标恢复以及失败重收均通过。恢复后新增仓库未混入原备份点。
- 远程 SSH 小样本测得停机 34.41 秒、总耗时 44.24 秒。尚未以生产数据量、限速大文件和人工流程完成对照，不能宣称达到 80% 人工节省指标。
- 后台浏览器固定副本操作与窄屏图标布局通过；通用导航 31 个入口往返通过。
- 初次真实验收在测试库缺表、默认 Docker 地址池耗尽及临时 IP 变化处失败，原日志保留在工作目录。修正隔离验收初始化和独立网段后重跑通过。一次进度写入锁竞争保留为原始证据，新增短事务提交后 SSH 整链路未再出现。
