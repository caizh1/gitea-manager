# 研发上库统计

在 Manager 侧栏打开「研发上库」，选择实例，点击「开始采集」。首次回补北京时间近 90 个自然日，之后后台按 15 分钟周期排队，也可发起立即采集。组织管理员通过当前授权绑定查看和采集组织仓库，平台管理员查看实例范围。

在「采集设置」中填写实际使用的缺陷标签，默认识别 `bug` 和 `缺陷`。可选择一个或多个 Gitea 团队供页面筛选，配置后开始保存日级成员快照。团队日报从可核实的成员日期开始列零活动行。为仓库配置生成物和第三方目录后，采集会以已保存的逐文件行数重算汇总。

如果要精确识别触发缺陷关闭的修复 PR，平台管理员可在「采集设置」输入 Gitea 服务端能访问的 Manager 根地址，确认该地址可通过 Gitea 自身的 Webhook 网络策略。具有对应写权限的实例令牌会在仓库创建专用的签名 Issue Webhook。回调只保存关闭时间、操作者和提交等配对证据。历史缺陷有关闭引用但缺少触发证据时显示「待归属」。签名关闭记录确认没有触发提交时，回溯关闭后的指派变更，使用关闭时的唯一指派人。

## 读数

- 「全部开发分支」按同仓首次可证明上库的 SHA 去重。「进入主线」按分支检查点核对 SHA 首次进入该仓库默认分支的时间。代码归 Git 作者，实际推送人在明细可查。Squash 产生单独的落地 SHA，明细附关联 PR。普通合并提交单列，两种视图分别统计。
- 变更行是新增与删除之和，使用 Git 对象逐文件核对。源码、文档、第三方、生成物、其他文本及二进制在明细中分列。缺失作者关联的提交和无法确认修复人的 Bug 单列待归属。
- PR 分别按创建与合并日期归 PR 作者。合并耗时中位数通过筛选范围内所有匹配的合并事件计算。待合并量为最近同步时的开放 PR。
- Bug 重开后撤回原关闭数，重新关闭时计入最终关闭日期。重开次数另计。通过 Gitea 缺陷单可查关单记录。
- Gitea 分支活动可能截断，历史也可能被清理。代码回补使用可核对的分支变更，未接入时无法证明默认分支归属的日期留出缺口。读取私有活动不完整时也显示采集覆盖说明。趋势的空心点表示当天已核实的部分记录。

## 隔离验收

使用官方 Gitea 1.26.4 可执行文件运行 `scripts/engineering-activity-acceptance.py --gitea <可执行文件> --output <隔离目录>`。脚本自行启动监听回环地址的 Gitea 和 Manager，生成两个组织、三个私有仓库和十二个研发账号。输出包含已核对的上库记录、前十、日报和 Bug 时间线；原生测试数据库和配置仅留在隔离目录。运行额外的后端边界和权限用例 `python -m unittest tests.test_engineering_activity tests.test_access_route_matrix`。
