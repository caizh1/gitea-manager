# Codex 审查失败诊断

## 本次内网反馈

2026 年 11 月 17 日收到内网任务失败反馈。工具调用和模型请求已有实时记录，随后出现红色会话状态。页面仅保留 `codex_failed`、`source=codex`、`reason=error` 和 Worker 调用栈。执行器原始诊断只有 73 字节。

现有容器日志和会话 SQLite 日志没有提供这次失败的具体错误正文，因此这次内网审查失败的原始原因仍待复测确认。

## 已修复的问题

- Codex 的错误正文原先放入只接收标识符的诊断字段，过滤后丢失。现在保存原始 JSONL 事件到任务诊断包，公开诊断使用稳定错误代码与阶段。
- Codex 的 stderr 原先直接丢弃。现在有界保存错误日志，精确移除本次会话凭据。原始诊断包中的文件为 `codex-stderr.raw`，超过保存额度时同时保存末尾片段。
- 失败状态原先先于诊断收尾暴露给 Worker，可能永久停留在“采集中”。现在先停止执行并固定诊断材料，再发布会话终态。
- Responses 网关原先未持久化 HTTP 拒绝和流内异常。现在保留本次模型调用的首个失败，携带调用编号、HTTP 状态、传输阶段、已接收长度及受控协议错误原因。随后 Codex 退出保留这条首因。
- 结果收集失败增加模型完成次数、回合完成状态、最终响应和最终文本是否收到等信息。

日志中的 PATH 别名只读警告已用原安装镜像复现，该命令退出码为 0。它不能单独证明审查失败。Gunicorn 的 128 退出记录早于本次最后一组模型与工具事件，现有材料无法确认该 PID 的身份和因果关系。

## 排查入口

打开失败任务详情，查看完整脱敏诊断。平台管理员可下载该任务原始诊断包，核对以下材料。

- `event-payloads.raw` 保存原始 Codex 事件，包括最终错误正文。
- `codex-stderr.raw` 保存进程错误输出。
- `model-response-<调用编号>.raw` 保存实际响应流。
- `manifest.json` 与 `causality.jsonl` 保存来源、摘要、截断状态和采集过程。

原始材料可能包含本仓库源码，沿用现有任务、组织、仓库及管理员授权检查，保留期限沿用原始诊断配置。升级只能改善后续任务的采集，已经丢失的正文无法由升级恢复。
