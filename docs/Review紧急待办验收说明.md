# Review 紧急待办：使用、验收与升级说明

## 本次交付

完成发布结果待核对的“发现 → 核对 → 解除阻塞 → 后续审查继续”。强制停止和全局暂停按已确认范围留待后续。

- 所有已登录页面的顶栏下方显示持续提醒，计数来自 Review 数据库，与历史表格分页、筛选和普通告警清除无关。
- Review 页面顶部展示前三个 PR；全部待办独立分页。排队任务显示“等待人工处理”，过期任务的阶段显示“版本已过期”。
- 全局入口打开全部待办，具体 PR 入口打开处理面板；深链接在重新登录后仍保留定位。
- 面板进入时自动请求一次只读发布核对，展示请求、开始、完成时间以及结果。无法确认时保留待办。
- 只有管理员明确确认原请求已经结束且未发布，并通过后端正式 Review／残留草稿复核，才能“确认未发布”。操作归属记录为“共享管理员”。
- 全局与顶部待办共享状态，每轮完成后 5 秒再次读取；恢复可见和操作完成时立即刷新。待办读取超时 5 秒，失败保留最后数据并显示更新失败。
- 旧版本任务进入或退出待核对状态都会通知当前 PR。更新后的 Gitea 组件显示或移除相同的阻塞原因。

## 人工基线与质量边界

目标用户是管理 Review 队列的共享管理员。输入是已有 Review SQLite 数据库、可访问的已配置 Gitea 和原有 Worker。支持既有单实例、Linux 本地持久卷部署，沿用官方 Gitea 1.26.4 和既有发布互斥；不新增模型依赖。

固定发现基准：两个真实隔离 PR，205 条合成过期历史，加上实际执行任务，共 212 条；待核对原任务位于第 11 页。复验过程中再次排入任务后为 213 条。旧流程按“事先不知道阻塞项位置，从第一页逐页查看”定义，需要 10 次翻页和 1 次打开详情；新流程由全局入口两次点击进入具体 PR。

- 发现／定位点击由 11 次降为 2 次，减少 **81.8%**；进入 Review 页面后也可从顶部直接一次点击处理。
- 实际浏览器已顺序点击第 2～11 页，固定提醒持续可见。
- 该指标是固定逐页查找基准，不是所有用户的最优操作路径，也不是内网人工耗时实验。已知末页位置并直接跳页的基线不适用。
- 待办分组覆盖 2/2；状态测试集中无重复累计、无遗漏、无错误解除。正式 Review 回执核对不重发；未发布分支保留必要的人工确认。
- 整条审核工作的人力减少 80%、真实内网模型准确率和现场用户实际耗时仍未验证。本次模型只使用协议替身验证工程流程，不衡量缺陷识别能力。

## 接口和状态

- `GET /api/ai-review/attention?page=1`：`summary` 始终覆盖全库，`items` 为按 PR 聚合的当前分页；可按 `repository`、`number` 定位。先分别聚合待核对与排队任务，再关联，避免多个阻塞项乘出重复排队计数。
- `GET /api/ai-review/tasks`：增加 `number` 和 `status` 筛选；`attention` 指向阻塞 PR，`reconciliation` 包含核对状态与时间。
- `POST /api/ai-review/tasks/<id>/reconcile {}`：仅排入只读核对；重复请求合并。
- `POST /api/ai-review/tasks/<id>/reconcile {"confirm_unpublished":true}`：管理员确认后的远端再次复核。
- 核对状态为等待执行核对、核对中、需要人工确认、核对失败、已解决。底层排队任务仍是 `queued`，未改动 Worker 的领取与阻塞规则。
- 新字段及通知触发器幂等创建，不复制到 Manager 告警表；原任务、配置、主密钥和历史记录保留。

## 离线交付和安装

本次完整包包含前端 dist、后端离线 wheels、Linux amd64 的 backend／frontend／executor 镜像、运行脚本及文档。使用固定镜像标签 `review-attention-20260915` 导出，按照现有完整 AI Review 打包器生成 `gitea-manager.tar.gz` 及对应 `.sha256`。

1. 将归档和校验文件复制到目标 Linux 主机，在归档所在目录运行 `sha256sum -c gitea-manager.tar.gz.sha256`。
2. 解压到独立升级包目录，进入该目录运行 `bash upgrade.sh`，按现有一键升级流程选择已有实例。保留原 Compose 项目、实际挂载、数据库、原 Review 主密钥和账号。
3. 组件启动使用现有离线镜像，禁止借升级重新生成已有 Review 的主密钥。维护、数据快照、健康与历史核对按原升级控制器执行。
4. Manager 升级后，在“AI Code Review → 仓库管理”按目标 Gitea 实例重新下载 PR 进度组件；它会写入该实例真实可信机器人 ID。将组件复制到 Gitea 主机，按组件内 `安装说明.md` 安装／升级并热重载模板。
5. 不要将隔离验收实例导出的组件 ZIP 安装到内网，它只信任测试机器人的 ID。完整部署包已包含新的组件生成器和资源；需要在目标 Manager 导出正确实例包。
6. 现场触发一条 PR 审查，检查全局提示、自动核对、真实 Gitea 卡片和后续任务领取。现场有未知发布记录时，先核对实际结果，不能仅因等待较久而确认未发布。

交付镜像复验会从最终归档导入镜像，在新建断网实例中运行，结果和归档 SHA-256 写入包旁的 `Review紧急待办-离线包复验.json`。构建、隔离实例及交付镜像复验均不能替代实际内网主机升级验收；本次未连接或修改用户内网环境。
