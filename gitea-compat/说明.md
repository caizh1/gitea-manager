# Gitea 1.26.4 草稿隔离兼容补丁

原版 Gitea 1.26.4 的 CreatePullReview API 在 event=PENDING 时仍调用提交逻辑。该逻辑创建公开 Review 时间线动态，并触发通知。实际测试中，普通开发者的 Review API 与文件页隐藏草稿，但 PR 时间线仍显示草稿正文及行内意见。

这是精准发布的必要前置问题：不能先公开尚未验证的位置，再依赖清理降低风险。

## 最小变更

补丁只改变 PENDING 的两个路径，增加一个模型层测试：

- 模型层仍提交保存草稿的数据库事务，但不生成公开 CommentTypeReview 动态。
- 服务层对 PENDING 返回，不访问空动态、不发送审查和代码评论通知。
- 正式 COMMENT、APPROVE、REQUEST_CHANGES 仍使用原来的提交与通知路径。

源版本：官方标签 `v1.26.4`，提交 `95ba37d9af58db7d9163f9e92e07b5eb4f792bbc`。兼容二进制版本标记为 `1.26.4+review.1`，不冒充未经修改的官方二进制。

源码差异见 `草稿隔离.patch`，许可证见 `LICENSE`。固定 Go 1.26.3，Linux amd64，使用 bindata、timetzdata、sqlite、sqlite_unlock_notify 和静态链接；前端资源从同版本官方 Gitea 二进制提取，避免更换前端行为。

## 部署关系

Manager 对原版 1.26.4 安全降级为普通总结，不创建带行内意见的 PENDING。只有明确受支持的草稿隔离兼容版本才启用先私有验证、后正式发布的流程。管理页面说明这一条件。

兼容镜像 `gitea-review-gitea:1.26.4-review.1` 随离线镜像归档交付，只替换官方 1.26.4 镜像中的 Gitea 二进制，保留基础环境。现有 Gitea 的数据卷、数据库、配置、权限和仓库无需迁移。本机测试使用独立实例，不自动替换现有生产实例。运维人员应先备份，再在原有 Gitea Compose 中显式选择兼容镜像，完成目标机验收后才启用行内审查。

不能用模板隐藏、缩短删除窗口或在评论中写“草稿”代替这项服务端修复；这些方式不能阻止通知和公开时间线提前暴露意见。

## 构建与离线边界

交付二进制、镜像和固定源码资源，运行时无需 Go、npm、下载或编译。构建准备机需要提前准备 Go 模块及工具链；编译阶段使用 GOPROXY=off、GOSUMDB=off 和断网容器。源码修改、编译器、二进制 SHA-256 与真实验证记录单独列入清单。

官方依据：[模型层 SubmitReview](https://github.com/go-gitea/gitea/blob/v1.26.4/models/issues/review.go)、[服务层 SubmitReview](https://github.com/go-gitea/gitea/blob/v1.26.4/services/pull/review.go)、[Review API](https://github.com/go-gitea/gitea/blob/v1.26.4/routers/api/v1/repo/pull_review.go)。
